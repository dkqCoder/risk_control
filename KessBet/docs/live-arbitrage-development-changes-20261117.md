# 滚球套利：按固定快照驱动的设计与开发清单

日期：2026-11-17（北京时间）  
性质：待开发实施说明；本文不表示功能已经完成。  
设计依据：用户确认的“获取数据 → 当次完整输入计算 → 命中保存原始数据 → 未命中等待下次变化”流程。原审核报告保留缺陷历史；本文件的第0节为最新实施主线。后文旧轮次问题是修复背景，已实现项按当前代码重新验收，不能直接视为尚未修改。

## 0. 最新主流程设计（本次修订的执行基线）

### 0.1 业务流程

1. 盘口或赔率推送到达，或比分/比赛阶段变化，触发本场数据刷新。
2. 获取完整原始盘口响应和请求前后比赛状态。若状态不一致则放弃本次计算、安排重取；若网络失败、空响应或无法确认可售状态，标记当前机会待确认/失效，不能继续展示旧机会。
3. 固定一个不可变输入快照：原始响应、解析选项、比分、阶段、半场信息及其可信来源、请求时间、过滤策略。所有计算输入都绑定snapshot_id。
4. 与上一份有效输入比较。影响计算或可售性的字段未变化则不重算；变化则计算。首次有效输入必须计算。
5. 从完整数据中挑选语义明确且受支持的盘口建模；求候选，再验证整个组合在无界可达终局中的最低收益。不能用“所有盘口都支持”的口号掩盖未知规则；不支持的选项保留原始记录并说明原因。
6. **验证成立**：持久化命中、完整固定输入及原始响应，生成固定证据页；可选异步截图。正式命中写库必须在验证之后。
7. **未发现套利**：更新本场当前状态，撤销上一机会，记录轻量计算日志，等待下一次变化。无需永久保留所有未命中的原始payload。
8. **无法判定**：与未命中分开，记录模型不完整、数据不一致、超时等原因，不沿用旧套利状态；等待重试或下一次变化。

截图不在计算与命中落库的关键路径。完整“原始数据”指实际用于本次计算的同请求输入，不能事后重新请求，也不能按时间找相近响应。

### 0.2 触发、合并与并发

- 触发包括：赔率变化、选项新增/删除/锁定/解锁、盘口变化、比分变化、阶段变化，以及规则或分析器版本变化。首次进入滚球范围也应拉取完整数据。
- 比分轮询发现影响计算的变化后，必须标脏并重取赔率形成新快照；只保存新比分不足以触发正确计算。取得新报价之前撤销旧机会的当前有效性。
- WS只作刷新信号，同场短时间信号合并；按完整响应的规范内容指纹确认是否真正变化。指纹不含纯接收时间，但包括可售状态、比分/阶段、有效半场上下文与规则/策略版本。
- 同场建议串行采集与计算；若允许并发，generation保证旧任务不能覆盖新状态。计算A期间到达B，A继续使用A快照，B单独排队，不拼接输入。
- 允许以最新快照合并尚未开始的任务，但必须说明系统并不保证捕获每个瞬时价格。若要求逐次响应都计算，应队列化，不静默丢弃。
- WS重连/断线后全量对账；低频对账用于补漏，不以每2秒强制全量重算代替变化触发。新鲜度到期可以单独使当前机会失效，无需重复求解相同输入。

### 0.3 保存策略

- 推荐复用当前不可变快照表作为短期输入缓冲，无需回退为纯内存：原始响应与解析数据、状态及当前指针原子发布。
- 所有采集快照可以先临时落表；命中时在同一逻辑事务中保存分析、组合、原始快照引用并设置永久保留，或复制完整输入进入证据记录。
- 未命中只长期保留snapshot_id/指纹、计算时间、版本、状态、耗时和错误等轻量日志；原始payload可按配置短期保留。清理不能删除正在计算、待取证或命中引用的输入。
- 无raw的诊断计算只能是内部结果；正式留证命中必须有完整同请求原始响应。存证事务失败不得发布“命中已保存”，需要幂等重试。
- 每条命中保存：snapshot_id、generation、analysis_id、事件身份、完整原始响应、规范输入、比分/阶段/半场来源、实际组合及赔率金额、规则/模型/分析器版本、最坏收益验证与时间区间。
- 不用秒级odds_updated作唯一输入身份；幂等键应包含snapshot_id及分析版本/策略指纹，不能让即时与周期入口重复写命中。

### 0.4 当前代码核对与剩余开发

最近只读检查已发现D01有进一步实现：`collect/live.py`以同一事务写入状态、赔率、不可变快照和当前指针；`evaluate_live_match()`已按current_snapshot_id精确加载输入。因此下文D01的“按最近时间关联”描述属于上一轮缺陷，不能继续断言仍在使用。事务故障和并发正确性仍需测试。

尚需优先完成：

1. **统一计算上下文**：将半场信息及可信来源固定到快照，不在分析中再读可变赔率历史；周期路径的比分、分钟、generation、response时间与持久化元数据全部取自被计算快照，不能夹带当前比赛行。
2. **变化驱动闭环**：比分/阶段变化触发重新取赔率；删除、空响应和失败明确失效；未变化只更新观察新鲜度，不重复求解；重试与对账补漏。
3. **正确计算再落命中**：实现D02的整组无界反例验证；other继续隔离，guard仅临时防线。正常开关维持关闭，直到正反验收通过。
4. **统一发布入口**：即时分析、周期补偿、CLI共用固定快照分析与资格校验，开关关闭不写正式命中；周期线程补偿未处理快照，不拼当前表也不强制重算已处理输入。
5. **命中存证与未命中等待**：事务保留完整输入；未命中/无法判定同步撤销旧机会，历史记录不删除。生命周期状态与历史计算记录分开。
6. **辅助证据与界面**：固定页展示本次输入，动态页面只显示当前有效状态；D03截图隔离作为补充工作，不阻塞接口原始数据留证主线。分析版本随行为变更升级。

当前配置仍关闭判定；本文不将磁盘开关等同于运行进程已生效。140项测试结果属于前一轮基线，不能冒充最近快照事务改动的回归结果。

### 0.5 主流程完成验收

- 一份有效完整输入 → 一次固定输入分析；重复同内容推送不重复求解/落命中。
- 赔率变化 → 新快照新分析；分析期间变价不会改变旧证据。
- 仅比分或阶段变化 → 立即撤销旧机会并重取赔率，形成新快照后计算。
- 套利验证通过 → 命中与同请求原始数据完整保存，离线可回放，不依赖官网或当前表。
- 不套利 → 当前状态变为未命中，不写套利记录，等待下一变化；无法判定有独立状态。
- 接口失败、明确停售、撤盘、过期 → 不沿用旧机会；恢复有效快照后才能重新发布。
- 周期路径计算和保存的比分、阶段、半场上下文及raw严格一致；不同入口同输入幂等。
- 7:0/9:0的小9.5+客队大0.5不能通过，输出10:0反例；存在真正无界覆盖的正向样例可通过。
- 临时输入清理不影响命中证据与在途计算；截图失败不影响已完成的原始数据存证。

## 2. 必改任务 D01：原始响应与计算输入精确绑定

优先级：P1；证据MVP阻塞项。

### 问题

上一轮缺陷是按15秒内最近时间关联raw、赔率与raw分别提交。最新代码已引入同事务固定快照及按ID读取；本任务转为核验其事务边界、并发、计算上下文与生命周期，保留下列要求作为验收而非断言尚未开发。

### 修改位置

- `collect/live.py`：原始输入归档、快照发布、采集回调。
- `db/dao.py`：赔率替换、原始响应保存、分析输入读取。
- `db/schema.sql`及新增迁移：快照身份和当前指针。
- `analyze/live/run.py`：周期分析与即时分析的输入统一。
- `web/api.py`、`web/evidence.html`：来源关联状态展示。

### 实现要求

1. 每次请求生成独立snapshot_id；同次raw、解析rows、请求前后状态、过滤策略和时间均绑定该ID。保留request_started_at、response_received_at；当前raw_time在后置状态请求之后生成，不能继续冒称实际收到赔率响应的时刻。
2. 原始响应与规范输入可存为同一不可变快照对象。若保留分表，在同一数据库事务内写raw、报价和快照指针；底层DAO不得各自提前commit破坏事务。
3. 当前赔率缓存记录所属snapshot_id，分析读取固定版本快照。即使当前指针随后变化，本次分析输入也不能变化。周期入口禁止拼接当前比分、可变赔率与“最近raw”。
4. 采集回调直接传同一snapshot_id；周期入口按ID加载相同快照，不能重新猜测时间。
5. `get_live_raw_near()`仅允许用于诊断，不能向正式证据链提供“同请求”保证。历史无ID记录保持raw缺失/关联未知，不自动回填。
6. 存档失败时保留采集错误日志和状态；不能把旧raw挂到新计算上。若保留无raw诊断计算，必须E0且不可认证。
7. 原始保留策略不得删除尚未分析或尚未复制到证据包的快照。以引用和任务状态控制清理，不能只假定最近5份总能覆盖分析延迟。
8. 用每场generation阻止较旧分析覆盖较新当前结果；固定历史分析可保留。

### 验收

- A/B两次请求在同秒返回、完成顺序相反，raw与rows仍精确一致。
- 在写赔率与存raw之间制造失败，不能出现可认证的新赔率配旧raw。
- 分析A时采集B，A证据依旧是A；B的当前结果不会被A晚完成覆盖。
- 缺少raw、迁移前旧数据、清理发生在分析期间，均明确降级，不按时间补证。

## 3. 必改任务 D02：关闭路径与白名单无界反例验证

优先级：P0；恢复可信判定的阻塞项。

### 问题与已复现输入

当前guard只拒绝任一队达到8球的场次。以下输入在当前7:0、85分钟时仍返回套利：

- 全场小9.5 @1.65；全场大9.5 @2.00。
- 客队大0.5 @5.70；客队小0.5 @1.10。

求解器选择小9.5与客队大0.5，但最终10:0全部输。低比分同样可能触发上限之外的亏损，不能通过提高G或调整guard阈值解决。

### 修改位置

- `analyze/live/result.py`：候选白名单、计算状态、独立验证调用。
- 建议新增 `analyze/live/verify.py`：独立结算与无界反例检查。
- `analyze/live/run.py`：两个入口共用结果发布策略。
- `collect/config.py`：运行开关和明确的影子模式。
- `web/api.py`：模型验证状态、反例及当前有效性。

### 实现要求

1. 保持判定关闭；补查 `analyze_live_once()`、CLI `--once`及采集回调。当前配置开关在回调和外层调度中生效不等于所有直接入口都受控，正式写库入口应集中检查。诊断force参数只能明确绕过计算调度，不能隐式绕过正式发布资格。
2. 首期白名单只开放常规时间全场1x2、Double Chance、BTTS，以及双边半球线全场/球队总进球。暂不认证比分盘、半场盘、让球、奇偶和组合盘。
3. 对选中的整组及配资，检查所有满足当前比分约束的无界整数终局是否存在非正或低于阈值的收益。实现可使用整数约束求解或经证明完备的阈值区域划分；不接受固定枚举上限充当无界验证。
4. 验证器直接按独立结算规则计算返还，不能调用同一soccer.STATES/covers循环重复证明有限模型。把赔率按固定精度保存，明确数值容差与金额取整规则。
5. 如验证器返回亏损反例，保存比分、各腿结算与总返还，标counterexample_found；超时/未知/非法输入标无法认证，不当作无反例。
6. 有限模型可暂用于找候选，但只有验证通过才可发布可信候选。它可能漏报，界面不得宣称穷尽全部套利。
7. `other`继续隔离。配置True不能直接恢复旧的 `FULL & ~named` 算法；要恢复须实现固定规则语义、规则版本及独立测试。
8. 对外成本按真实腿计算，保留当前ghost剔除逻辑；独立重算实际金额的最低收益。不要将模型公式推得的收益称为已经验证的真实最低收益。

### 验收

- 9:0及7:0案例均拒绝，并给出10:0反例。
- 当前较低比分下的高比分尾部、比分差和双方再进球均覆盖到。
- 构造真实无界覆盖的正向白名单组合，能够通过；不能靠关闭全部判断冒充算法修复。
- 求解未知、超时、赔率非法、取整后利润不达标均不通过。
- 两条分析入口、CLI直接调用在开关关闭时都不写正式命中。

## 4. 必改任务 D03：官网截图任务隔离

优先级：P1；证据MVP阻塞项。

### 问题

`common/platform_shot.py`仍固定9333端口与kessbet_shot_profile目录。多个命中daemon线程可能连接同一CDP页面，互相导航或终止浏览器，造成A文件名保存B页面。

### 实现要求

- MVP可先使用单一有界截图worker串行执行；确保所有调用方共用同一调度，不只是对单个线程局部加锁。若允许多进程，进程内锁不够，应集中任务队列或完全隔离会话。
- 并行方案须每个worker独立端口、配置目录与目标页面身份；连接时检查自己创建的target，不默认取第一个page。
- 任务使用evidence_id与snapshot_id，明确页面所有权和超时退出；只清理自己启动的进程/配置。
- 选择All失败不得静默退回Main后宣称覆盖；返回实际tab、页面身份、覆盖状态和原因。Main图可保存为部分补充。
- 截图前验证URL/比赛身份；保存capture_started_at、capture_finished_at、响应至截图延迟以及是否覆盖目标。
- 对共享会话风险的修复不能只依赖图片文件名唯一。

### 验收

- 同时提交两场任务，截图内容、URL和文件身份一致，互不干扰。
- 第一任务超时或浏览器退出，第二任务能继续且不继承错误页面。
- All不存在、目标未渲染、页面跳回首页均产生明确的部分/失败状态。
- 图片存在且>1KB但实际为错误页面，不得标为页面核验成功。

## 5. 必改任务 D04：动态页面不得套用历史组合

优先级：P2；上线前完成。

位置：`web/live_detail.html:chosenBySelection()`、`renderMarkets()`，以及`web/api.py:live_detail()`。

当前仍只按market|side|line|label匹配，因此旧组合的配资比例会贴在当前新价格上；改名“内部组合”不足以解决数据错配。

首选MVP：动态全部盘口中移除组合标记与配资，固定证据页展示历史组合。若确需保留，必须同时满足：分析有效、当前快照ID等于分析快照ID、平台选项ID匹配、赔率精确一致、判定未暂停。缺任一项不显示。

历史比分、时间、收益统一标为“计算时”，不得称“当前”。分析暂停后详情、列表、首页汇总和命中列表均不能把旧成本<1当作当前机会。仅在详情页加暂停提示不是全站修复。

验收：新价格同名盘口、暂停判定、版本变更、过期、缺失选项时均无当前组合标记；固定证据页内容不变。

## 6. 必改任务 D05：分析版本与历史回放兼容

优先级：P2；新证据写入前完成。

位置：`analyze/live/run.py:LIVE_ANALYZER_VERSION`、回放函数及证据API。

本轮已经改变other隔离、比分guard及ghost成本，版本仍为live-result-b2-v2。应升级分析器版本，并为结算规则、状态空间、候选策略分别记录版本/配置指纹。仅升级常量不足以兼容旧记录。

要求：

- 新记录持久化实际运行的版本与影响结果的配置，不仅是代码默认值。
- 旧版本回放可选择保留对应实现，或明确返回unsupported_version；不能用新算法重跑后误称历史数据损坏。
- 若使用当前算法重算历史输入，显示为新分析，并关联原analysis/snapshot，不覆盖旧结果。
- ghost剔除造成成本差异时，不使用放宽容差掩盖算法版本变化。

验收：修改前后同输入生成不同版本；旧版本的含other/ghost快照得到明确兼容结果，不出现“同版本不可复现”的误导。

## 7. 证据MVP的边界与补充要求

当前固定页是正确方向，但仍属于E0/E1。以下条件达到前不开放E2：

- 原始响应与分析输入通过ID精确绑定，而非时间猜测。
- 平台事件/市场/选项身份、可售标记、规则版本及全部组合可追溯。
- 整个组合的无界覆盖和取整后最低收益已验证。
- 原始数据、规范输入、分析结果可导出并离线复核；记录来源和时间，建议manifest及SHA-256。哈希不能单独证明官网来源或可信时间。

E2可以由合格同请求接口响应支持，截图不是硬性前提；标签写“平台接口报价已核验”。浏览器后来变价不否定历史接口响应，但会使当前机会失效。截图范围内未见选项，只能记not_covered，不能推断平台不存在。

本地冻结页截图是内部报告的副本，真正主证据是保存的原始平台响应及其可验证关联，不能把“内部页面不可变”直接等同于“平台报价已证实”。

## 8. 历史记录处置与部署

1. 保持配置关闭，核查实际运行进程已经加载；单改磁盘文件不能证明后台已停止。
2. 用户提供76条统计作为待核对线索。先只读导出ID、时间、组合、回放输入，独立确认范围，备份后追加invalid/原因字段或独立审计表；不删除、不直接覆盖旧证据。
3. 已确认的F01/F02错误记录停止作为有效套利展示；证据不足的记录标未核验，不虚构逐条反例。
4. 原始表迁移在启用读取代码之前完成；存档失败不能让分析因缺表整体崩溃，也不得伪造raw。
5. 分批发布：停判定及历史展示修复 → 精确快照、固定页、截图隔离 → 无界白名单验证 → 影子运行 → 人工抽查正反样例 → 恢复正式发布。
6. F03空响应/撤盘、F05状态及半场未知等已知问题可后续扩展，但恢复范围内的必要失效约束必须先完成；不能把它们笼统延后再认证当前有效报价。

## 9. 开发提交与完成标准

建议拆为五个可独立审阅的修改：

1. 精确快照关联与迁移（D01）。
2. 截图隔离和动态展示防误导（D03/D04）。
3. 无界白名单验证、统一写库资格（D02）。
4. 分析版本与历史回放（D05，可随各变更同步升级）。
5. 证据导出、历史审计与部署检查。

每次提交提供：具体变更、复现输入、正向及失败测试、迁移步骤、运行限制。运行现有相关回归，并增加各任务验收场景；涉及真实数据库事务和浏览器隔离的测试单独执行，不能仅用mock冒充联调。

全部任务完成并有测试证据前，结论应写“止血及证据基础已完成/部分完成”，不得写“真实套利已可靠识别”。恢复判定必须同时满足：F01/F02不再误报、输入精确绑定、当前有效性闭环、无界正反样例通过、页面和接口证据不混淆。
