# bet365 赔率抓取

> 最后更新：2026-11-09
> 状态：**已跑通**，能自动拉取任意联赛的全套赔率。

## 一句话结论

bet365 的体育内容接口**不接受外部 HTTP 调用**（只要调用方不是页面自己，
就返回 200 + 0 字节）。唯一可靠的方式是开一个真实 Chrome，
在页面上下文里调用**站点自己的 `Loader` 类**发请求。

已经有封装好的实现：`collect/bet365/browser.py`。

```bash
py tools/bet365_probe.py                       # 英超 20 场 1X2 全量
py tools/bet365_probe.py --league 135650998    # 英冠
py tools/bet365_probe.py --json                # 结构化输出
```

## 为什么必须用浏览器（踩坑记录）

这一节记录的是一次完整的误判过程，避免以后重复踩。

| 尝试 | 结果 | 结论 |
|---|---|---|
| 纯 HTTP + 正确 cookie | 200，0 字节 | 不是 cookie 问题 |
| 加 `X-Net-Sync-Term` token | 200，0 字节 | 不是 token 内容问题 |
| 真实 Chrome 里裸 `fetch()` 同一 URL | 200，0 字节 | **不是浏览器指纹问题** |
| 抓成功请求的完整头重放 | ✅ 25618 字节 | token 与请求绑定 |
| 页面里 `new ns_datalib_net.Loader()` | ✅ 正常返回 | **这才是正确方式** |

关键理解：

1. `Loader.load()` 内部走 `xcft()` → 向页面派发 `xcftr` 事件 →
   页面内混淆脚本回填 `xcft<instanceCounter>` 事件 → 得到与该
   **Loader 实例**绑定的 `X-Net-Sync-Term`。
2. 裸 `fetch` 不经过这套流程，所以永远是空响应。token 拿在手里复制出去也没用——
   它和 `instanceCounter` 绑定。
3. 还有个隐藏条件：**页面必须已经发生过一次路由活动**。
   刚打开首页就 `new Loader()` 请求，依然返回 0；先切到一个联赛页、
   等它渲染出赔率，之后 Loader 才稳定可用（`browser.py` 的 `_activate()` 处理这个）。

另外两条环境限制：

- Chrome 不能带 `--enable-automation`（`navigator.webdriver === true` 时
  足球页渲染不出内容）。`browser.py` 用 CDP 直连，不走 Playwright。
- 无头模式下 `ns_datalib_net` 可能初始化不出来，默认用有窗口模式。

## 接口链路

### ① 盘口目录

```
GET /contentdata/matchmarketscontentapi/markets
    ?lid=10&zid=0&cid=197&cgid=2&ctid=197
    &pd=%23AC%23B1%23C1%23D1002%23E{联赛ID}%23G40%23H%5E1%23
```

页面描述符 `#AC#B1#C1#D1002#E91422157#G40#H^1#`：

| 段 | 含义 |
|---|---|
| `AC` | 联赛/比赛页 |
| `B1` | 运动：足球 |
| `D1002` | 页面类型 |
| `E91422157` | 联赛编号（英超） |
| `G40` | 分组 |
| `H^1` | 子页 |

实测英超 20 场、16 个盘口、20 KB。

### ② 单盘口

把目录里 MA 行的 `PD` 路径原样传回同一个接口，拿到该盘口的全部选项赔率。

## 数据格式

`text/plain`，`|` 分隔记录、`;` 分隔字段。复杂点在于**顺序有意义**：

```
PA;ID=PC257789315;NA=曼城;N2=富勒姆;FD=曼城 v 富勒姆;FI=203186235;
   BC=20261121123000;EX=puw~.../match/72221406~...;PZ=0;     ← 比赛表
PA;ID=PC257790163;...;PZ=1;
...                                                          ← 20 场，PZ 0..19

MG;ID=40;SY=cmx;                                             ← 盘口组
MA;MA=40;ID=M40;NA=1;FI=203186235;...                        ← 列头：1
PA;ID=257789315;FI=203186235;OD=12/25;PZ=0;                  ← 各场「主胜」
PA;ID=257790163;FI=203186239;OD=1/1;PZ=1;
...
MA;...;NA=X;FI=203186235;...                                 ← 列头：X
PA;...                                                       ← 各场「平」
MA;...;NA=2;...                                              ← 列头：2
```

**MA 行是列头，其后连续的 PA 行按 PZ 对齐到各场比赛。**
`league.parse_market_odds()` 就是按这个规则实现的。

| 字段 | 含义 |
|---|---|
| `FI` | 比赛编号，贯穿比赛表与赔率行 |
| `FD` | 比赛全名 `主队 v 客队` |
| `BC` | 开赛时间 `yyyyMMddHHmmss`（**英国时间**，不是 UTC） |
| `EX` | 含 Sportradar 比赛 ID：`.../match/72221406~` |
| `OD` / `OX` | 赔率，**英式分数**，`12/25` → 1.48 |
| `PZ` | 排序，比赛在列中的位置 |

`parse.fractional_to_decimal()` 处理分数换算，`league.py` 负责把列头 + 赔率对齐成
`{比赛名: {1: 1.48, X: 4.5, 2: 6.0}}`。

## 验证

`test_bet365_league.py` 用真实快照跑了 15 项断言，包括：

- 20 场比赛、60 个赔率的计数
- 具体赔率值（曼城 1.48 / 4.5 / 6.0）
- Sportradar ID 抽取正确
- **覆盖成本落在 1.03~1.12**——这条最有价值，解析错位时它会立刻失败

## 已知限制

1. **依赖真实浏览器**，每场比赛几秒，不是纯 HTTP 的毫秒级。
   要跑全量建议复用同一个 `Bet365Browser` 实例，不要每场新建。
2. **开赛时间是英国时间**，入库前要按 `common/timeutil.py` 转北京时间。
3. **折叠盘口拿不到**（见下节）。
4. bet365 的服务条款禁止自动化抓取，且对无牌照地区做地域封锁。
   仅供个人数据分析，自行评估风险。

## 折叠盘口与 WebSocket（2026-11-09 实测）

### 现象

单场 coupon 接口的盘口目录里，部分 MG 记录只有名字和 PD、没有赔率：

```
MG;ID=M10203;NA=Exact Total Goals;DO=0;PD=#AC#B1#C1#D8#E203186235#G10203#I6#S^1#;
MG;ID=981;NA=Goals Over/Under;DO=1;PD=;          ← DO=1，后面有完整的 MA/PA
```

`DO=0` 的就是**折叠状态**。Goals 标签页 42 个盘口里，只有 14 个带内容，
其余 28 个（Exact Total Goals / Clean Sheet / Winning Margin …）都是折叠的。

### 试过但没用的办法

* 用 `PD` 路径直接请求 `coupon` / `markets` / `partial` → 全部 200 + 0 字节
* 换 tab（I1/I3/I6/I7/I18/I19）→ 折叠盘口在哪个 tab 都是空的

### WebSocket 推送能拿到什么

单场页会建立 WebSocket，推送的赔率帧是这个格式：

```
\x14PM203186235-257789317\x01
F|PA;DO=4.5;FI=203186235;ID=257789317;OD=7/2;RS=1;SU=0;|
```

* topic `PM{比赛ID}-{选项ID}`
* `DO` 十进制赔率、`OD` 分数赔率、`RS=1` 可投注、`SU` 状态

**但推送是增量的**：实测在单场页停留、滚动触发全部懒加载后，
只收到 3 个 1X2 选项的帧（436 字节）。没有变化的盘口不会推，
所以**单靠 WS 拼不出完整快照**。

routing 表里能看到推送 topic 的定义（`P_CONFIG` / `P-ENDP` 帧给的端点清单），
其中 `/matchbettingcontentapi/soccerbetboost` 这类也是推送驱动。

### 结论

| 数据 | 拿法 | 完整性 |
|---|---|---|
| 联赛页 1X2 / 大小球 / BTTS / 双胜彩 | 纯 HTTP（浏览器 Loader） | 完整，20 场 |
| 单场 15 个主力盘口（含正确比分） | coupon 接口 I1 | 完整，592 赔率 |
| 亚盘 / 球线 | coupon 接口 I3 | 完整，8 个盘口 |
| 大小球细分 | coupon 接口 I6 | 14/42 个盘口有内容 |
| 半场盘 | coupon 接口 I7 | 9 个盘口 |
| **折叠盘口**（Exact Total Goals 等） | — | **拿不到** |
| 实时变动 | WebSocket | 仅增量，不能拼快照 |

**做套利分析够用**：覆盖成本计算主要靠 1X2、大小球、亚盘、BTTS 这几类，
它们都在「完整」那一档里。折叠盘口是球员数据、精确比分细分这类，
本来也不参与状态空间求解。

如果确实要折叠盘口，目前唯一已知的路是**真实浏览器逐一点开**
（每次点击触发一次增量请求），成本和复杂度都高，暂不实现。

## 与 KessBet 的对比

| 项 | KessBet | bet365 |
|---|---|---|
| 取数方式 | 纯 HTTP + AES 加密请求体 | **真实浏览器 + 站点 Loader** |
| 响应 | JSON | 竖线分隔文本 |
| 赔率格式 | 小数 | **英式分数** |
| 认证 | 硬编码 key | 页面内生成的实例绑定 token |
| 反爬 | 出口 IP 黑名单 | 拒绝非页面内调用 |
| 难度 | 低 | **高**（需要浏览器） |
