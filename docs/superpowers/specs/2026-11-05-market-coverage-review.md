## 二、复核方法

原文用**盘口白名单匹配**判定覆盖：把 `covers()` 源码里出现过的
`base == '...'` 提取成集合，剥掉队名/半场前缀后查表。

我的方法不同：**实际调用 `collect_from_rows()` 生成候选池**，
看每个盘口有没有真的产出候选。两者应当一致，差异只在边界情况。

### 2.1 白名单法是否高估覆盖

白名单说某盘口「已覆盖」，但 `covers()` 可能因 label 不匹配返回 `None`
（例如 `1x2` 的 label 若不是 `1`/`X`/`2`）。

实测 20,000 个 `(market, side, line, selection)` 组合：

| 盘口 | 白名单内 | 实际返回 None | 失败率 |
|---|---|---|---|
| Handicap | 38,070 | 150 | **0.4%** |

只有 Handicap 有极少量标签异常，其余盘口失败率为 0。
**白名单法在这个数据集上是准确的**，原文的数字可信。

### 2.2 数字复核

跑原文 §6 的复现脚本：


## 三、HT/FT Correct Score：收益真实但有限

### 3.1 原文的论断

> P1 | 补 `Halftime/Fulltime Correct Score` | 49,450 | 最大体量，与 Correct Size 同构 | 中
>
> 这是漏报套利的真实来源。`Halftime/Fulltime Correct Score` 一个盘口
> 就近 5 万选项，它的高赔率具名选项能补覆盖窄缝，原理和昨天修的
> Correct Score 一样 —— 具名比分进池后能降低最小覆盖成本。

### 3.2 实测（更正后）

我实现了 HT/FT 的 mask 生成（`'0:0 1:1'` → 半场 0:0 且全场 1:1；
`'4+'` → 该维度总进球 ≥ 4），先抽取 80 场对比：

```
样本: 80 场（均有 Halftime/Fulltime Correct Score，LIMIT 80 无 ORDER BY）
HT/FT CS 内部 Σ(1/odds): min=1.562  中位=1.618  max=1.731
加上 HT/FT 后成本下降: 0 / 80 场
```

**这个 0/80 是错的 —— 原因在抽样，不在数据。**

### 3.3 抽样偏差：为什么 0/80 是假象

同样的掩码实现，把样本换成「未来 72h 内**全部**有该盘口的比赛」再看：

| | 场次 | min | 中位 | < 1.3 的场次 |
|---|---|---|---|---|
| 我的 80 场样本 | 80 | **1.562** | 1.617 | **0** |
| 未来 72h 全部 | 376 | 1.226 | 1.583 | **9（2.4%）** |
| 全库 | 1,059 | 1.218 | 1.583 | 30（2.8%） |

我的查询是 `LIMIT 80` 且**没有 `ORDER BY`**，取到的 80 场
`min=1.562`，一场都没落进 < 1.3 的尾部。

**收益恰恰全部来自尾部。** 对那 9 场逐场实测：

| match_id | 原成本 | 加 HT/FT | 差值 | 内部和 |
|---|---|---|---|---|
| 245062239680237637 | 1.055896 | 1.052220 | **−0.003676** | 1.256 |
| 245148684487006042 | 1.031304 | 1.031304 | 0 | 1.259 |
| 245148688781972497 | 1.028124 | 1.028124 | 0 | 1.226 |
| 245062239680237629 | 1.044872 | 1.044872 | 0 | 1.249 |
| 245148693076939018 | 1.028205 | 1.024038 | **−0.004167** | 1.234 |
| 245062239680237633 | 1.052092 | 1.049779 | **−0.002313** | 1.227 |
| 245062239680237641 | 1.054377 | 1.054377 | 0 | 1.256 |
| 245062239680237766 | 1.052381 | 1.043290 | **−0.009091** | 1.234 |
| 245148688781973637 | 1.029476 | 1.029476 | 0 | 1.259 |

**9 场中 4 场改善（44%）**，进最优解的全部是 `HTFTCS|0:0 0:0`。

勘误另找的 4 场（不同样本）也独立复现成立，
成本下降 0.0023–0.0091，覆盖 2025/2025 完整，LP 方向一致。

### 3.4 mask 完备性独立验证

46 个标签的 mask：**并集 = FULL（2025/2025），重叠 0 对，无法解析 0 个**。
`4+` 按「该维度总进球 ≥ N」实现是自洽的。

（唯一残留的不确定性：第二段 `4+` 到底是「全场总进球 ≥4」还是
「全场某队进球 ≥4」。这不影响上述结论 —— 4 场改善全部由
`0:0 0:0` 驱动，未依赖任何 `4+` 标签。）

### 3.5 关于「差一个 `other`」—— 这条推理是错的

我第一版写：HT/FT 没有 `other`，具名比分构不成窄缝，所以进不了最优解。

**这条推理不成立。** 反例来自昨天 Correct Score 的修复本身：

```
match 245064451588395947 最优解（cost=1.066374）:
   1st Half - Correct Score|||1:2    [具名比分]
   1st Half - Correct Score|||2:1    [具名比分]
   1st Half - Correct Score|||2:2    [具名比分]
   1st Half - Correct Score|other    [other 补集]
   1st Half - Total||2.5|under       [普通盘口]
```

具名比分与 `other` **同时在最优解里**，不是「靠 `other` 才进得去」。
两者互补：`other` 是「大覆盖、中赔率」的兜底，具名是「小覆盖、高赔率」
的精准补缝。**精准补缝不依赖兜底选项存在。**

我把「CS 恰好有 `other`」这个观察，错误地当成了「具名能进池的前提」。

### 3.6 更正后的定性

- **不是「最大漏报来源」**（原文夸大）：受影响约 2–5% 场次，
  最大降本 −0.009，判定翻转 0 场。
- **也不是「收益为 0，不做」**（本文第一版的错误）：确实有场次受益，
  机制与 Correct Score 同构、已验证。
- **正确定性**：收益有限的建模扩展。是否投入取决于
  「约 2% 场次小幅降本」值不值得这份工作量。

## 四、其他逐项核实

### 4.1 HT/FT 标签歧义 —— 原文判断错误

原文（转述 HANDOFF）：

> 标签有歧义（`0:0 4+` 既可能是"半场 0:0 → 全场主队 4+"也可能是
> "全场总进球 4+"）。HANDOFF.md 的判断是对的：在拿到官方说明前不要猜。

我抽取 2,000 个真实标签核查：

```
含 `4+` 的标签共 476 个，形态：
   '0:0 4+'  '0:1 4+'  '0:2 4+'  '0:3 4+'  '1:0 4+'
   '1:1 4+'  '1:2 4+'  '2:0 4+'  '2:1 4+'  '3:0 4+'  '4+ 4+'

非两段式（用空格切分）的标签: 0 个
```

**100% 是 `"半场 全场"` 两段式。** `4+` 出现在第一段是「半场总进球 ≥4」，
出现在第二段是「全场总进球 ≥4」——**位置决定含义，不存在歧义**。
`'4+ 4+'` 两段都有也照样解析得通。

HANDOFF 这条判断本身就是错的，原文只是转述没有验证。

> 残留不确定性：第二段的 `4+` 到底是「全场**总进球** ≥4」还是
> 「全场**某队**进球 ≥4」，从标签本身仍无法 100% 确定。
> 但已有的 `'3:0 4+'` 与 `'4+ 4+'` 并存，若 `4+` 指某队进球，
> 则两者语义重复 —— 更支持「总进球」的解释。
> 这不影响 §3 的收益结论：4 场改善全部由 `0:0 0:0` 驱动，未涉及 `4+`。

> 结论：**标签无歧义，不构成 P1 的前置阻塞。**
> 真正要权衡的是 §3 说的收益规模（约 2–5% 场次小幅降本）值不值得投入。

### 4.2 Draw No Bet —— 语义描述错误

原文：

> 平局退款。等价于 1x2 去掉平局后归一化，语义简单

**「等价于去掉平局后归一化」是错的**，会误导实现。

Draw No Bet 只有 `1` / `2` 两个选项（`SELECT selection ... GROUP BY` 验证：
`1` 有 2,404 个，`2` 有 2,404 个，**没有 `X`**）。平局时**退还本金**，
不是「该选项不存在」。

正确语义：`'1'` 覆盖「主胜」状态集，`'2'` 覆盖「客胜」状态集，
平局状态下两者净收益都是 0（退本金）。这与纯覆盖模型不同——覆盖模型
假设「没选中就输光」。直接按 `win_mask` 建模会**低估赔付**，
在平局密集的场景可能高估收益。

不过实测下来这不是问题：

```
样本: 80 场（均有 Draw No Bet）
DNB 内部 Σ(1/odds): min=1.1782  中位=1.1999  max=1.2039
加上 DNB 后成本下降: 0 / 80 场
```

**收益同样是 0。** 内部和 1.20 比现有最优组合贵，进不了最优解。

原文 P2 把 DNB 列为「语义明确，工作量小」——工作量确实小，
但收益也为 0，不该排进优先级。

### 4.3 Multiscores —— 标签有损，不可建模

原文：

> 多比分组合（如 `1:0, 2:0`）。标签含逗号，`parse_mari` 已能解析，`covers` 没接

`parse_mari` 能**提取出字符串**，但标签本身是**有损的**。真实样本：

```
'0:1, 0:20:3'      ← 是 "0:1, 0:2, 0:3" 还是 "0:1, 0:20" + "3"?
'1:0, 2:03:0'      ← 第二个逗号丢了
'1:2, 1:31:4'      ← 同上
'2:3, 2:4, 3:41:5' ← 第三个逗号丢了
'4:0, 5:06:0'      ← 同上
'other awaywin' / 'other homewin' / 'X'
```

用 `re.findall(r'(\d+):(\d+)')` 提取会得到**错误结果**：

```
'0:1, 0:20:3'  ->  [('0','1'), ('0','20')]   ← ('0','20') 是错的，应为 ('0','2')
'1:0, 2:03:0'  ->  [('1','0'), ('2','03')]   ← ('2','03') 是错的，应为 ('2','0')
```

平台的拼接规则存在丢逗号的情况，**没有可靠办法还原**。
这不是「`covers` 没接」，是**数据本身不足以建模**。

> 除非拿到官方对这条拼接规则的说明，否则 Multiscores 应当归入
> 「状态空间表达不了」而非「能补」。

全库规模：19,096 选项 / 1,736 场。

> 注：本文与原文的选项数有细微差异（如 HT/FT CS 本文 49,496、原文 49,450；
> Draw No Bet 本文 4,816、原文 11,706），因为两次统计的时间点不同，
> 且原文按「盘口名 + 队名变体」分别计数。量级和结论不受影响。
> 本文所有数字均为复核当次实测。

### 4.4 1x2(xup) —— 原文的「疑似」是合适的

原文说「疑似去掉某项后的 1x2」。我对比了同一场比赛：

```
1x2:       1=2.160  X=3.850  2=2.850
1x2(xup):  1=1.980  X=3.650  2=2.550   (line='2up')
Handicap:  0:1  1=3.250  X=4.000  2=1.550
```

**三个选项都在**，不是「去掉某项」。赔率比 1x2 整体略低，`line` 有
`2up` / `3up` 两种。含义仍不明——可能与「某队净胜 2 球以上」有关，
但没有依据。

原文标「疑似」而不下结论是正确的。全库 3,276 选项 / 955 场。

### 4.5 Which Team Wins The Rest Of The Match

原文列了 54 个选项，归入「能补」，理由是「需要当前比分维度」。

实测标签就是标准 `1`/`X`/`2` 三个：

```
1=2.700  X=2.700  2=2.800
1=1.700  X=3.400  2=4.450
```

确实需要知道「当前比分」才能建模（这是在滚球盘用的），而我们的分析
只处理赛前盘 `odds_prematch`。**在赛前状态下，它等价于全场 1x2**，
属于重复盘口。原文判断正确。

规模 54 选项 / 18 场，可忽略。

### 5.1 角球为什么值得做

原文的 P3 思路是对的，理由值得保留：

- 角球是独立计数，不共享足球的 `(h1,a1,h2,a2)` 状态空间
- 可以单独建 `analyze/covers/corners.py`，状态空间就是「角球总数」
- 复用现有的 `solver.solve()` 和 `payout.lp_solve()`，不需要改核心
- 不会与足球比分模型互相污染

**但同样要先实测。** 按本次的教训，在写代码前应当先：

1. 取全部有角球盘口的比赛（**不要 `LIMIT` 取样，要全量看分布**）
2. 用真实赔率构造角球状态空间的候选
3. 算内部 Σ(1/odds) 的**全分布**，重点看尾部有多少场 < 1.3
4. 对尾部场次逐场实测收益
5. 再决定是否投入

现有四个角球盘口（`Total Corners`、`Corner 1x2`、`Corner Range`、
`Odd/Even Corners`，含半场变体共 7 个）。还需确认里面有没有
**覆盖极窄的选项**（如「正好 0 个角球」）—— 那是收益能否出现的
关键前提，见 §6.2。

## 六、方法论沉淀

本次复核遇到两个陷阱，都值得记下。

### 6.1 「能建模」≠「有收益」

一个盘口能不能进候选池，取决于两件事：

1. **语义能不能映射到状态空间**（能不能写 `covers()`）
2. **映射之后能不能进最优解**（`1/odds` 相对现有盘口有没有优势）

原文只考察了第 1 点。第 2 点要看两个东西：**盘口内部 Σ(1/odds)** 和
**它有没有覆盖极窄的选项**。

### 6.2 内部和快筛：第一版给的判据是错的

我第一版写「内部和 > 1.3 直接放弃」，**这条会误杀 HT/FT**：
它的中位 1.583，但尾部 2.4% 的场次内部和 < 1.3，那些场次恰恰有收益。

删掉这条判据。改为看**全分布**，不是中位数：

| 盘口 | 内部和分布 | 尾部（<1.3）占比 | 实测收益 |
|---|---|---|---|
| 正常全场盘口 | 1.02 – 1.09 | — | 是（进最优解） |
| Correct Score | 1.37 – 1.52 | 低 | 8/250 场改善 |
| Halftime/Fulltime CS | **1.218 – 1.768** | **2.4%** | **4/9 尾部场次改善** |
| Draw No Bet | 1.10 – 1.25 | 100% | **0/80** |

DNB 是反例：内部和全部低于 1.3，却零收益。**说明内部和低是必要条件，
不是充分条件。**

### 6.3 真正的判据：有没有「覆盖极窄」的选项

把三次实验放在一起看，能同时解释所有结果的，是**单选项覆盖的状态数**：

| 实验 | 能进最优解的选项 | 覆盖状态数 | 赔率 | 收益 |
|---|---|---|---|---|
| Correct Score | `1st Half - CS 1:2` / `2:1` / `2:2` | 72 / 72 / 72 | 30 / 26 / 100 | ✅ 有效 |
| Halftime/Fulltime CS | `0:0 0:0` | **1** | 高 | ✅ 有限有效 |
| Draw No Bet | `1` / `2` | **约 900 各** | ≤ 2.85 | ❌ 无效 |

**收益来自「精准补缝」：一个覆盖极少状态、赔率很高的选项，
能以极小的增量补上别的盘口漏掉的那几个状态。**

判据：

```
补盘口前，先看它有没有「覆盖状态数 ≤ 10」的选项。
没有 -> 直接放弃（DNB 这类，选项都是大覆盖，永远不会是补缝的那一块）
有   -> 再看这些窄选项的赔率：1/odds 是否小到能改善覆盖
        最后，全量（不取样）统计内部和分布，对低尾部场次实测
```

这条判据能解释为什么 CS 和 HT/FT 有效、DNB 无效，而内部和这个指标
单独看会误导。

### 6.4 抽样必须覆盖分布尾部

第一版的核心错误就在这里：`LIMIT 80` 无 `ORDER BY`，取到的 80 场
`min=1.562`，而总体 min=1.218。**收益全在尾部，抽样却正好避开了它。**

规则：

- 候选集合**全量统计分布**（不算 ILP，只算内部和，很快）
- 如果分布有明显长尾（如 p10 与 min 差很大），**必须对尾部单独取样**
- 抽样要排序（按内部和升序），不要依赖数据库的自然顺序
