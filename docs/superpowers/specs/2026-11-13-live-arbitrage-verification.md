## 一、Handicap 盘线语义确认

### 1.1 为什么要查

2026-11-13 发现一条假套利，`Handicap 0:1` 的 `2` 在 0:0 时被定价 100.00。
按我们的模型，`0:1` 表示「客队 +1 让球」，`2` = 客队不输，0:0 时**必然成立**，
应该是 1.05 左右。定价 100 意味着模型可能整个反了。

**如果语义反了，所有用让球盘做的覆盖计算都是错的。**

### 1.2 方法：用 Correct Score 做基准

`Correct Score` 的标签是 `1:0` / `0:1` 这种，**语义没有歧义**。
同一时刻的 CS 赔率可以算出各终局的隐含概率，据此推出任意让球线下的真实概率：

```
P('1') = Σ P(终局)   满足 主队进球 + hl > 客队进球 + al
P('X') = Σ P(终局)   满足 两边相等
P('2') = 1 - P('1') - P('X')
```

再和 Handicap 盘口自己的赔率反推概率对比。若「1↔2 互换」比原样更吻合，说明语义反了。

### 1.3 结果：8 个快照全部支持原样

```
455177 @ 2026-11-12 09:53:13   当时比分 2:0
  line 0:1     赔率 1@1.57  X@3.2  2@4.05
    Correct Score 推出: 1=0.546  X=0.260  2=0.194
    Handicap 反推:      1=0.532  X=0.261  2=0.206   ← 误差 0.026

310515 @ 2026-11-12 03:13:44   当时比分 0:0
  line 1:0     赔率 1@1.37  X@3.9  2@4.55
    Correct Score 推出: 1=0.555  X=0.246  2=0.200
    Handicap 反推:      1=0.605  X=0.213  2=0.182   ← 误差 0.101
```

**8 个快照无一例外，「原样 1/X/2」都是最吻合的假设。**

**结论：`line 'H:A'` = (主队让 H 球, 客队让 A 球)，`1`/`X`/`2` 按让球后比分判定。现有 `covers()` 实现正确。**

复现：`py tools/check_handicap_semantics.py`

## 二、临场假套利的三次追查

### 2.1 第一次：Turkiye vs Belgium Σ=0.898（未定论）

- 下注组合：`Handicap 2:0` 的 1@1.5 / 2@14.0 / X@6.25
- 三个选项来自**同一个盘口同一条盘线**，内部和 0.898

单一盘口内部和不可能 < 1。但当时数据已清理，无法定位成因。
**记录为「待查」，后由 2.2 / 2.3 解释。**

### 2.2 第二次：Equatorial Guinea Σ=0.1312

下注组合：`1x2 · 1 @8.25` + `Handicap 0:1 · 2 @100.00`

流水时间线：

```
01:40:36  line=1:0  2 @50     第77分钟
01:47:34  line=1:0  2 @75     第84分钟
01:47:56  line=0:1  2 @80     第85分钟   ← 盘线标签在这里变了，价格却连续
01:50:07  line=0:1  2 @100    第87分钟
```

价格从 50 平滑爬到 100，说明**被调价的是同一个结果**，只是标签变了。
这正是「盘线串门」的特征 —— 详见第三节。

### 2.3 第三次：Atletico Morelia Σ=0.7465（这是另一个原因）

```
11:11:08   4 条赔率变动   比分 0:0  第49分钟   ← 赔率最后一次更新
11:11:58   ★ 命中 Σ=0.7465   第50分钟 1:0      ← 状态已是 1:0
11:12:35   16 条赔率变动  比分 1:0  第51分钟   ← 赔率这才跟上进球
```

**进球后，状态（10 秒轮询）先更新，赔率（推送触发）还没重新定价。**
中间 87 秒里，分析拿「1:0 的可达终局」去套「按 0:0 定的赔率」，
两个世界的价格硬拼在一起。

前后各查一次成本都正常（1.09~1.11），只有中间这段是错的。

**这道防线：`odds_updated` 必须 >= `score_changed_time`。**

## 三、解析器「盘线串门」bug

### 3.1 症状

同一时刻、同一盘线、同一选项出现两个不同赔率：

```
01:38:29  line=2:0  2 @4.400
01:38:29  line=2:0  2 @10.500
01:38:29  line=2:0  X @3.700        ← 这一组完全没有 `1`
```

一个三选一盘口出现两个 `2`、没有 `1` —— 结构性错误。

### 3.2 根因

`parse_mari` 里：

```python
for chunk in section.split('^'):
    for seg in chunk.split('@'):
        parsed = _split_selection(seg)
        if parsed is None:
            continue                    # ← 盘线名跟着这一段一起丢了
        line, label, odds = parsed
        if line:
            current_line = line         # ← 只有解析成功才更新
        sels.append((current_line, label, odds))
```

**盘线的名字写在每条盘线的第一个选项那一段里。** 如果这个选项被锁定（`,0,`）
或赔率为 0，`_split_selection` 返回 None → `continue` → 盘线名丢失 →
后面所有选项继承**上一条盘线**。

### 3.3 修复

把「取盘线名」和「解析选项」拆开。判据是原始串的结构：

```
{盘线,}{selId}/{标志}={selId},{赔率},{标志},{标签}
         ↑ 带盘线的段：逗号后紧跟 `\w+/[01]=\w+,`
{selId},{赔率},{标志},{标签}
         ↑ 普通段：没有 `=`
```

```python
_LINE_PREFIX_RE = re.compile(r'^\w+/[01]=\w+,')

def _line_prefix(seg):
    if '|' in seg:                       # 剥掉 `matchId,tabId|`
        seg = seg.rsplit('|', 1)[-1]
    head, _, rest = seg.strip().partition(',')
    return head if _LINE_PREFIX_RE.match(rest) else ''
```

使用：

```python
prefix = _line_prefix(seg)
if prefix:
    current_line = prefix            # 先更新盘线，与选项是否有效无关
parsed = _split_selection(seg)
if parsed is None:
    continue
sels.append((current_line, label, odds))
```

### 3.4 A/B 验证

同批原始串，分别用旧/新逻辑解析：

```
60 场 / 2882 个盘口
  解析结果有差异: 5 个 (0.17%)
    其中 Handicap: 4 个
```

典型差异（Qatar vs Australia）：

```
旧: ('3:0','1',1.03), ('3:0','X',6.4), ('3:0','2',14.0), ('3:0','X',6.8), ('3:0','2',18.0)
                                                        ↑ 3:0 里混进了 4:0 的选项
旧内部和 3:0 = 1.401

新: ('3:0','1',1.03), ('3:0','X',6.4), ('3:0','2',14.0), ('4:0','X',6.8), ('4:0','2',18.0)
新内部和 3:0 = 1.199, 4:0 = 0.203
```

修复后复检 2882 个盘口：**「同一盘线重复标签」= 0**。

复现：`py tools/check_parse_ab.py`、`py tools/check_dup_labels.py`

## 四、被推翻的 4 个结论（重要）

### 4.1 ❌「滚球窗口盘 35% 残缺」

早期文档（11-09 设计稿、11-10 复核稿）都引用了这个数字。

**实际是判定脚本写错了**：脚本检查 `labels == {'over','under'}`，
但窗口盘的标签是 `'over 0.5'` / `'under 0.5'` —— 阈值嵌在标签里。
所有 `Total` 类被误判成残缺。

按 `(match, market, side)` 正确分组后重算：

```
kessbet_odds_prematch   34 组   残缺 0
kessbet_odds_history    30 组   残缺 0
```

**真实残缺率是 0，不是 35%。**

### 4.2 ❌「100.00 是停盘占位价」

我曾断言 75/100 这类赔率是平台停盘时的占位值。**没有证据，是从「内部和不合理」倒推的。**

用平台页面验证后推翻：

```
Sonio Takamatsu 0:2 Blancdieu Hirosaki   85'
1x2   1 @100.00（可点击）   X @8.50   2 🔒（锁定）
```

而且流水显示它是**连续演变**的：

```
01:40:36  2 @50    01:45:50  2 @70    01:48:44  2 @90
01:41:20  2 @55    01:47:34  2 @75    01:50:07  2 @100
01:42:02  2 @60    01:47:56  2 @80
```

**这是真实定价**（主队大比分落后、时间将尽，主胜几乎不可能），不是占位符。

### 4.3 ❌ 第一版盘线修复（逗号在斜杠前）

第一次修复用的是「逗号出现在 `/` 之前就算带盘线」。
A/B 测试立刻发现它把 `Halftime/Fulltime` 的标签 `1/1`、`X/2` 误判成盘线：

```
旧: ('', '1/1', 3.25), ('', '1/X', 15.0)
新第一版: ('245172624634712556', '1/1', 3.25)   ← 把 selId 当成盘线了
```

改用「逗号后紧跟 `\w+/[01]=\w+,`」的判据才对。

**这个错是 A/B 测试抓到的，不是靠推理。**

### 4.4 ❌「`replace_live_odds` 双提交是 Atletico Morelia 误报的成因」

`replace_live_odds` 确实有两个 commit 之间新旧数据共存的窗口（已改为单事务）。
但查流水后确认，11:11 那次误报的成因**是比分/赔率不同步**，不是双提交。

两个问题都真实存在，但不是同一个。

## 五、数据质量实测

### 5.1 同一场比赛的赔率新旧跨度

```
Portland Trail Blazers   8002 秒（2.2 小时）
New Orleans Pelicans     8354 秒（2.3 小时）
```

成因：`replace_live_odds` 的删除只在收到 WS 推送时执行。某盘口停推、
其他盘口还在推 → 停的那批行留在表里。

而 `odds_updated = MAX(updated_time)` 仍然新鲜 → 新旧混排被当成有效数据。

**防线：行级一致（`max_lag_sec=120`）** —— 只保留跟得上本场最新采集的选项。

### 5.2 三选一盘口的内部和分布

```
扫描 172,273 行流水，6311 组三选一盘口

内部和分布: min=0.246  p1=0.768  中位=1.108  p99=2.215  max=2.304
  < 0.50 : 42 组 (0.67%)
  < 0.90 : 66 组 (1.05%)
  < 1.00 : 67 组 (1.06%)
```

**中位数 1.108** —— 单一博彩公司内部必然有抽水，这个分布符合预期。
1.06% 的异常组全部集中在 `1st Half - Handicap`，后确认为盘线串门。

复现：`py tools/check_market_sum.py`

### 5.3 231 轮滚球采样：残缺盘口是常态

```
总抓取轮次     231
  无异常       140
  有可疑项      91（127 个盘口）

「同一盘线重复标签」= 0        ← 解析器 bug 消失
127 个可疑项全部是「平台锁掉一条腿」
```

按盘口分布：

```
Double Chance                    62
1st Half - Both Teams To Score   26
1x2                              15
Both Teams To Score               9
1st Half - 1x2                    5
1st Half - Total                  3
Total                             3
其它                              4
```

典型形态：

```
Both Teams To Score
  yes  0.00,0   ← 锁定（原始串标记 ,0,）
  no   4.90     ← 唯一可投注
Σ = 0.2041
```

**这类盘口自己无法构成覆盖，但剩下那条腿可以和别的盘口拼。**
而平台锁腿通常意味着「这个盘口马上要结算」—— 剩那条腿的价格是冻结的。

**防线：缺腿盘口整组剔除**（按标签集合是否齐全判断）。

复现：`py tools/watch_live_raw.py`、`py tools/check_incomplete_markets.py`

### 5.4 盘线为空的合法性

窗口盘和很多结果盘的 `line` 列**恒为空串**（阈值嵌在 selection 标签里）：
`'over 1.5'` 而不是 `line='1.5'` + `label='over'`。

**早期文档要求「同一盘口内 line 必须一致」是错的判据** —— line 全是空串，
这条检查永远通过，挡不住任何东西。

## 七、六道防线的完整清单

| # | 位置 | 防线 | 判据 | 失败时的行为 |
|---|---|---|---|---|
| 1 | `collect/kessbet/parse.py` | 盘线前缀独立解析 | 逗号后紧跟 `\w+/[01]=\w+,` | 丢弃该选项，保留盘线名 |
| 2 | `db/dao.py:replace_live_odds` | 单事务替换 | upsert + delete 同一事务 | 整体回滚 |
| 3 | `analyze/live/run.py` | 赔率新鲜度 | `now - odds_updated > 90s` | 不告警（仍写成本） |
| 4 | `db/dao.py:get_live_selections` | 行级一致 | 比本场 `MAX(updated_time)` 早 120s 的行丢弃 | 该行不参与判定 |
| 5 | `analyze/live/run.py` | 赔率必须比比分新 | `odds_updated < score_changed_time` | 跳过整场 |
| 6 | `analyze/live/result.py` | 缺腿盘口剔除 | 标签集合不齐 | 整组剔除并告警 |

### 7.1 关于第 3 道的取舍

赔率过期时**仍然重算**，只是不告警。原因：

```
18:20:46  算出 cost=1.1073，选中 Total H 4.5 over/under
18:21     解析器修复，4.5 被识别为锁定并删除
          → 但赔率超过 90 秒没更新 → stale_odds 一直跳过重算
          → 结果表里永远留着引用已不存在选项的记录
```

**成本必须永远反映库内当前数据**，过期只影响「要不要当成机会告警」。

### 7.2 关于第 6 道

和已关闭的「内部和 < 阈值」不同：

| | 判据 | 性质 |
|---|---|---|
| 内部和 < 0.9 | 统计口径 | 可能误伤正常的残缺盘口 |
| 标签集合不齐 | 结构判据 | 确定，不会误伤 |

实测当前 3 场：去掉残缺盘口后成本完全不变（1.0978 两种算法一致），
说明这道防线目前不做多余的事。
