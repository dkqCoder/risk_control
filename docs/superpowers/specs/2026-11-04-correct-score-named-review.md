## 三、证伪：原文的量化论证站不住

### 3.1 两个「证伪」测的其实是同一件事

原文证伪一称「修复后 cost = 0.665」，证伪二称「修复后 cost = 0.687」。
我把这两组赔率单独求和：

```
证伪一 CS 盘口内部 Σ(1/odds) = 1/9 + 1/7 + 1/8 + 1/3.5 = 0.664683
证伪二 CS 盘口内部 Σ(1/odds) = 1/50 + 1/1.5           = 0.686667
```

**两个数字与原文的「修复后 cost」完全相等。**

这说明原文测到的不是「具名比分让整体成本下降」，而是
**「一个自身已经低于 1 的盘口被加进了候选池」**。
任何内部 `Σ(1/odds) < 1` 的盘口加进去都会得到同样结果，
与具名不具名无关 —— 把 `other` 单独加进去也一样。

换句话说，这两个用例证明的是「独立套利的盘口能降低整体成本」，
这是个恒真命题，不构成对「具名比分不会进最优解」的反驳。

### 3.2 这些赔率在真实数据里不存在

抽取 30 场真实 `Correct Score` 盘口，计算各自的内部 `Σ(1/odds)`：

```
min = 1.367    median = 1.507    max = 1.522
```

**区间完全在 1.0 以上**，且相当集中（1.37–1.52）。
原文的 0.665 远低于真实分布的边缘 —— 这不是「常见赔率结构」，
是手工构造的异常定价，而且异常到了真实数据里不会出现的地步。

### 3.3 真实影响：250 场实测

「按原文修复方案追加具名候选」求解 ILP：

### 3.4 变化最大那场的实际机制

`245064451588395947`，ILP 成本 1.085252 → 1.066374：

```
当前组合：
  1x2 X                  odds 未入选
  Double Chance 12
修复后组合：
  1st Half - Total 2.5 under   odds 1.07  覆盖 521 个状态
  1st Half - Correct Score other      odds 20.00
  1st Half - Correct Score 1:2        odds 30.00
  1st Half - Correct Score 2:1        odds 26.00
  1st Half - Correct Score 2:2        odds 100.00
```

`1st Half - Total 2.5 under` 赔率 1.07（`1/odds = 0.9346`），
覆盖 521 个状态，是个极便宜的「大覆盖」选项；它漏掉的那几个
半场比分状态，恰好由三个高赔率具名比分补齐。

**这个案例确实推翻了「不会进最优解」的断言** —— 具名比分进了最优解。
但它让成本从 1.085 降到 1.066，两头都在 1.0 以上，判定不变。
**这正是缺陷的真实形态：影响成本精度，不影响告警判定。**

## 五、确认为真的部分

### 5.1 缺陷方向安全

「候选池只增不减 ⇒ 最优成本只会下降或不变」
这个推理正确。250 场实测**无一场成本上升**，与推理一致。
缺陷方向是漏报（成本高估），不会把无套利误判成有套利。

### 5.2 第四节 NO_COVER 可复现

```python
rows = [('Correct Score','','','0:0',9.0),
        ('Correct Score','','','1:0',7.0),
        ('Correct Score','','','other',3.5)]
```

实测输出：

```
n_cand = 1        status = no_cover
other 覆盖 2022/2025 状态
状态 (0,0,0,0) 是否被 other 覆盖: False
```

属实。补充一点原文没说的：若盘口里**只有** `other` 而没有具名比分，
`if other and named` 会让 `other` 也不进池，候选数为 0 ——
这个分支比原文描述的更脆弱一些。

### 5.3 修复方案正确

按原文方案（具名进池 + `other` 仍用 `FULL & ~named`）在
`245064451588395947` 上验证：

| 检查项 | 结果 |
|---|---|
| 候选数 | 242 → 276 |
| 覆盖完整性 | **2025 / 2025，完整** |
| 具名与 `other` 重叠状态 | **0**（互斥成立） |
| ILP 求解 | ok |
| LP 求解 | ok |
| 交叉验证 | LP 与 ILP 方向一致（LP 更优，符合允许部分下注的预期） |

语义检查：`1st Half - Correct Score` 的 `1:2` 覆盖 72 个状态，
起点为 `(1,2,1,2)`、`(1,2,1,3)`… —— 半场比分锁定为 1:2，
全场比分自由，**mask 语义正确**，没有和全场 `Correct Score` 混淆。

原文修复方案的「为什么正确」四条理由，逐条验证通过。

## 六、建议

### 6.1 应该修

理由不是「漏掉了大量套利机会」，而是：

1. **设计理由确实是错的** —— 「不会进最优解」已被单场案例直接推翻
   （`245064451588395947` 的具名比分进了最优解）
2. 代码里留着一个基于错误前提的特殊分支，会持续误导后来维护者
3. 成本会普遍性小幅下降，数字更准
4. 代价确实很小：每场多约 34 个变量（242 → 276），求解无感

### 6.2 不该按原文强度立项

- **0/250 翻转**意味着这个修复不会改变告警行为。
  按「修复漏报的真实套利机会」写进 commit 或文档，会误导后续的优先级判断。
- 原文验证计划第 3 步「全库对比确认无场次成本上升」需要跑几千场 × 2 遍 ILP，
  成本很高而预期收益（验证一个理论上必然成立的单调性）很低。
  本次 250 场的实测已足够支撑「无成本上升」。

### 6.3 回归用例要重写

原文建议的用例若按它给出的赔率构造
（`1x2 2.5/3.2/2.7` + `CS 9/7/8/3.5`），测的是
**「一个独立套利的盘口拉低整体成本」**，而非具名比分的贡献。
这样的用例在修复前后会一直绿，什么都没证明。

要测具名的真实贡献，应该用：**盘口内部和 ≥ 1、但具名比分仍能改善覆盖**
的赔率组合。可直接拿 `245064451588395947` 这一场的真实赔率做夹具
（成本 1.085252 → 1.066374），它满足这个条件。
