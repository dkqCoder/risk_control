## 二、滚球盘口的三个层次

真实数据里，足球滚球盘口分三类，**判定逻辑完全不同**：

### 2.1 时间窗口盘（自包含）

```
5 Minutes - Total Corners From 76 To 80     第 76~80 分钟的角球总数
10 Minutes - Booking 1x2 From 71 To 80      第 71~80 分钟谁得牌多
```

**关键特征：不需要当前比分。**

`5 Minutes - Total From 76 To 80` 问的是「第 76~80 分钟进了几个球」，
和之前进了几个球无关。三个选项（over/under 或 1/X/2）覆盖该窗口全部结果。

**判定**：`Σ(1/赔率) < 1` 即套利。

### 2.2 全场结果盘（需要当前比分）

```
Total               总进球（含已进的）
Correct Score       终场比分
Handicap            让球
```

**关键特征：必须知道当前比分。**

`Total 2.5 over` 在 0:0 第 10 分钟和 2:0 第 70 分钟含义完全不同。

### 2.3 剩余时间盘（需要当前比分）

```
Which Team Wins The Rest Of The Match
```

**关键特征：从当前比分起算**，但标的是「接下来谁赢」。

## 三、实测数据：内部和

| 盘口类型 | Σ(1/赔率) 范围 |
|---|---|
| `5 Minutes - Booking 1x2` | 1.1141 ~ 1.1163 |
| `5 Minutes - Corner 1x2` | 1.1206 ~ 1.1220 |
| `5 Minutes - Total Corners` | 1.1190 ~ 1.1247 |
| `5 Minutes - Total Bookings` | 1.1141 ~ 1.1190 |
| `10 Minutes - *` | 1.1128 ~ 1.1270 |
| `15 Minutes - *` | 1.1023 ~ 1.1294 |
| `Which Team Wins The Rest Of The Match` | 1.1034 |

**全部 > 1，最低 1.1023。抽水 10.2%~12.9%。**

与 11-09 那次赛前采样的结论一致（1.095~1.153）。两批独立数据给出同一量级。

### 3.2 完整性问题

11-09 的统计发现 31 组里 11 组残缺（35%）。这次 22 组都有 ≥2 个选项，但样本太小。

**完整性检查仍然是必需的** —— 残缺数据会算出 `Σ = 0.12` 这种假信号。

## 四、判定模型

### 4.1 模型 A：时间窗口盘独立判定（先做这个）

```python
def check_window_arbitrage(selections):
    """对每个时间窗口盘口，算内部 Σ(1/odds)。

    这类盘口自包含：N 分钟内的 1x2 三选项就覆盖了该窗口全部结果，
    不需要和其他盘口组合，也不需要当前比分。
    """
    hits = []
    for market, sels in group_by_market(selections):
        if not is_window_market(market):
            continue
        if not is_complete(market, sels):     # ← 关键防线
            continue
        cost = sum(1 / s.odds for s in sels)
        if cost < 1.0:
            hits.append({'market': market, 'cost': cost, 'selections': sels})
    return hits
```

**为什么先做这个：**
- 不依赖比分（比分延迟未验证）
- 不碰现有状态空间
- 代码量最小

**`is_complete()` 的判据：**

| 盘口 | 需要的选项 |
|---|---|
| `N Minutes - 1x2 From A To B` | `1`、`X`、`2` 三个 |
| `N Minutes - Total From A To B` | `over`、`under` 两个 |
| `N Minutes - Corner 1x2` | `1`、`X`、`2` 三个 |
| `N Minutes - Booking 1x2` | `1`、`X`、`2` 三个 |
| `N Minutes - Total Corners` | `over`、`under` 两个 |
| `N Minutes - Total Bookings` | `over`、`under` 两个 |

**同一个盘口内 `line` 必须一致** —— 如果 `Total From 76 To 80` 里混了
`line=0.5` 和 `line=1.5`，不能一起算。

### 4.2 模型 B：全场结果盘（需要比分，暂缓）

核心是把状态空间参数化。**这里有一个关键的设计选择**（见 11-09 文档的
审核意见）：

**B2：四元组状态子集（推荐）**

```python
# 状态空间仍是 (h1,a1,h2,a2)，但只保留「当前比分可达的终局」
# 当前 1:0 时，可达终局是 h2>=1 的那些
live_idx = [IDX[s] for s in STATES if s[2] >= home_score and s[3] >= away_score]
```

- 可复用现有 `covers()` 的 mask（语义不变：`h2+a2 > 2.5` 仍正确）
- 不需要把「全场 line」换算成「剩余 line」
- solver 的 `n_states` 从 2025 变成子集大小

**为什么不用 B1（二元组「剩余进球」空间）：**
- 必须重写整套 `covers_live()`
- `Total` 是最终结果盘（含已进球），在「剩余进球」空间里要换算 line
- 容易错

### 4.3 模型 C：时间窗口 + 分钟数（不建议）

状态空间随时间变化，复杂度最高。首期不做。

## 五、必须先解决的问题

### 5.1 比分更新延迟（硬阻塞模型 B）

`hmp`/`amp` 是平台抓的现场数据。从现场进球到平台更新有延迟。

**如果延迟几十秒，模型 B 的判定就是错的** —— 你以为 1:0，实际已经 1:1。

**怎么测**：在比赛进行中，连续高频采样（每 1 秒一次）`fetch_state`，
同时记录本地时间。当 `hmp`/`amp` 变化时，说明平台更新了。
但「现场实际何时进球」无法从接口获知，只能：

1. 和平台的直播文字播报对比（如果有）
2. 或者接受这个延迟，在设计上留安全边际

**当前状态：未测。** 后台 `watch_live.py` 需要在足球赛进行时跑。

### 5.2 滚球赔率的时效性

滚球赔率秒级变动。从「采到赔率」到「人看到」到「实际下注」，
可能已经变了。

**这意味着：**
- 滚球套利的命中必须标注精确时间戳
- 页面上要显示「数据延迟」
- 实际可用性取决于下注速度

### 5.3 结算规则未验证

滚球盘口的结算规则可能和赛前不同。比如：
- `5 Minutes - Total` 的窗口是从开赛算还是从当前时刻算？
- 进球后是否立即结算？

**这些规则必须确认**，否则会产生假套利。就像之前 HT/FT 那次，
用「完备互斥」验证了 `4+` 的语义。

## 六、建议的实施顺序

### 阶段 1：模型 A（可以立即做）

```
1. 写 analyze/live/ 模块
2. 实现 is_window_market() / is_complete() / check_window_arbitrage()
3. 接入 analyze 的事件循环，对滚球比赛跑模型 A
4. 命中写入套利快照表（复用 kessbet_arbitrage_snapshot，加 live 标记）
```

**验收**：
- 不产生假套利（`is_complete` 挡住残缺数据）
- 命中时留存完整盘口快照

**预期结果**：大概率零命中（抽水 10%~13%）。但这本身是有价值的结论 ——
说明单家平台滚球定价自洽，要找机会得跨平台。

### 阶段 2：只记录不判定

如果模型 A 零命中，先不急于做模型 B。改为：

```
每场比赛快照「时间窗口盘的内部和」到一张表
积累 1~2 周后，统计：
  - 有没有场次接近 1.0
  - 抽水分布的形状
```

这比直接做模型 B 更稳 —— 先搞清楚数据里到底有没有机会。

### 阶段 3：模型 B（视阶段 1/2 结果）

只有在证明「滚球定价确实有破绽」时才投入。

## 七、数据质量问题

### 7.1 大量篮球数据混入

当前 `kessbet_odds_live` 里 32/34 场是篮球，足球只有 2 场。

原因：采集 `live_matches()` 没有按 sport 过滤，把篮球也采了。

**这需要决定：**
- 如果只做足球套利，采集应该加 `sport='sr:sport:1'` 过滤，省资源
- 如果将来要做篮球，现在的数据结构是对的

**建议**：保持现状（都采），但分析只处理足球。篮球数据将来可能有用，
而且采集中文名对存储压力不大。

### 7.2 篮球的状态码未映射

实测看到 `ms=13/14/15/16`，含义未确认。如果要做篮球套利必须先补测。

### 7.3 分析进程还没接滚球

现在的 `analyze/run.py` 只处理赛前（`WHERE kickoff_time > NOW()`）。
滚球数据只采不算。
