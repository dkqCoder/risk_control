# 套利判定逻辑

> 本文档说明系统如何判断"这场比赛有没有套利空间"。
> 配套代码：`analyze/covers/soccer.py`、`analyze/solver.py`、`analyze/run.py`

---

## 一句话概括

把每个盘口选项翻译成"它覆盖哪些可能结果"，然后求一组选项：
**覆盖所有可能结果，且总成本最低**。如果这个总成本 < 1，就是套利。

---

## 一、什么叫"套利"

假设一场比赛只有三种结果：主胜、平、客胜。

```
主胜赔率 5.20  →  花 1 元押主胜，中了拿回 5.20
平局赔率 3.60  →  花 1 元押平局，中了拿回 3.60
客胜赔率 1.56  →  花 1 元押客胜，中了拿回 1.56
```

如果我按比例分配，让任何一种结果中奖都能收回 1 元：

```
押主胜 x 元、平局 y 元、客胜 z 元，满足：
  5.20x = 1
  3.60y = 1
  1.56z = 1

解得：x = 1/5.20 = 0.1923
      y = 1/3.60 = 0.2778
      z = 1/1.56 = 0.6410
      
总投入 = 0.1923 + 0.2778 + 0.6410 = 1.1111 元
```

**投入 1.1111 元，不管什么结果都收回 1 元，亏 0.1111 元。**

这 11.11% 就是**平台抽水**（vigorish / margin）。

```
Σ(1/赔率) < 1  →  投入 0.98 元收回 1 元，赚 0.02 元  ← 套利
Σ(1/赔率) = 1  →  不赚不亏
Σ(1/赔率) > 1  →  投入 1.11 元收回 1 元，亏 0.11 元  ← 正常
```

**套利判定就是求 `Σ(1/赔率)` 的最小值。** 因为可以自由选择买哪些盘口，所以要找"最省钱的那组"。

---

## 二、难点：盘口不止三个

上面只有 3 种结果，很容易。但实际情况是：

- 一场比赛有 **71~95 个盘口**
- 每个盘口有多个选项，总共 **300~500 个选项**
- 结果空间远不止"胜平负"三种

**关键问题：怎么知道"所有可能结果"是什么？**

不能简单枚举"主胜/平/客胜"，因为还有：

- 总进球数（0、1、2、3…）
- 半场比分
- 双方是否都进球
- 让球后谁赢

**如果只用 1x2 三项，就漏掉了所有其他盘口的组合机会。**

---

## 三、解决方案：状态空间

把一场比赛的**完整结果**定义成一个四元组：

```
(h1, a1, h2, a2)

h1 = 半场主队进球
a1 = 半场客队进球
h2 = 全场主队进球
a2 = 全场客队进球
```

### 取值范围

```python
h1, a1 ∈ 0..5    # 半场最多 5 球
h2, a2 ∈ 0..9    # 全场最多 9 球
```

### 约束

```
h2 >= h1    # 全场进球不可能少于半场
a2 >= a1
```

### 状态总数

满足约束的组合共 **2025 个**。

举例：

| 状态 | 含义 |
|---|---|
| `(0, 0, 0, 0)` | 半场 0:0，全场 0:0 |
| `(0, 0, 1, 0)` | 半场 0:0，全场 1:0 |
| `(1, 0, 1, 0)` | 半场 1:0，全场 1:0 |
| `(0, 1, 2, 3)` | 半场 0:1，全场 2:3 |
| `(2, 1, 3, 2)` | 半场 2:1，全场 3:2 |

**这 2025 个状态就是"所有可能发生的结果"。**

### 为什么选这四维，而不是别的

#### 理由 1：半场信息是必需的

**实测：42.6% 的选项（30,731 / 72,151）依赖半场信息。**

| 盘口 | 依赖 |
|---|---|
| `1st Half - Total` / `1st Half - 1x2` / `1st Half - Handicap` | 上半场 |
| `2nd Half - Total` / `2nd Half - 1x2` | 下半场 |
| `Halftime/Fulltime`（1782 选项） | 半场 + 全场 |
| `Halftime/Fulltime Correct Score`（4738 选项） | 半场 + 全场 |
| `Highest Scoring Half` | 两个半场对比 |
| `To Win / Score In Both Halves` | 两个半场 |

**反例**：全场 2:0 有两种可能——
「上半 2:0 下半 0:0」（`Halftime/Fulltime` = `1/1`）
和「上半 0:0 下半 2:0」（= `X/1`）。
**只记全场比分无法区分这两注。**

#### 理由 2：存半场 + 全场，下半场自动得出

```
下半场主队进球 = h2 - h1
下半场客队进球 = a2 - a1
```

一个四元组覆盖三个时间维度：

| 维度 | 取法 |
|---|---|
| 上半场 | `(h1, a1)` |
| 下半场 | `(h2 - h1, a2 - a1)` |
| 全场 | `(h2, a2)` |

所以不需要额外存下半场。代码里：

```python
def _half_goals(state, side, first):
    h1, a1, h2, a2 = state
    if first:
        return h1 if side == 'H' else a1
    return (h2 - h1) if side == 'H' else (a2 - a1)
```

#### 理由 3：更细的粒度不值得

**能不能加上时间维度（每 15 分钟比分）？**

实测依赖具体时间的盘口只有个位数（`10 Minutes - 1x2`、`5 Minutes - Total`
等滚动盘，足球里几乎不出现），而半场相关的是 3 万多个选项。

加时间维度会让状态数指数级爆炸，却只多覆盖极少盘口。

#### 注意：`h2` 是全场，不是下半场

两种写法的代价对比：

| 写法 | 约束 | 代价 |
|---|---|---|
| 半场 + **全场**（当前） | `h2 ≥ h1` | 下半场要相减 |
| 半场 + **下半场** | 还要保证 `h1 + h2 ≤ 9` | 约束复杂，全场要相加 |

选前者，因为所有半场判断都能退化成求和/相减，逻辑最简。

### 状态数推导

```
h1, a1 ∈ 0..5  →  36 种半场比分
对每个 (h1, a1)，全场有 (10-h1) × (10-a1) 种
总和 = Σ (10-h1)(10-a1) = 2025
```

> **为什么这样就够**：任何盘口（总进球、比分、双方进球、让球…）都是
> 由这四个数字计算出来的。只要一个组合覆盖了全部 2025 个状态，
> 不管比赛打成什么样，都必有一注中奖。

## 四、每个选项 = 一个 bitmask

### bitmask 是什么

用 2025 个二进制位表示：
- 第 i 位 = 1 表示"这个选项在第 i 个状态上会中奖"
- 第 i 位 = 0 表示"不会中奖"

### 实际覆盖率

实测数据：

| 选项 | 含义 | 覆盖状态数 | 占比 |
|---|---|---|---|
| `1x2 \| 1` | 主胜 | 895 | 44.2% |
| `1x2 \| X` | 平局 | 235 | 11.6% |
| `1x2 \| 2` | 客胜 | 895 | 44.2% |
| `Double Chance \| 1X` | 主胜或平 | 1130 | 55.8% |
| `Total 2.5 \| over` | 总进球 ≥3 | 2010 | 99.3% |
| `Total 2.5 \| under` | 总进球 ≤2 | 15 | 0.7% |
| `Handicap 0:1 \| 1` | 主让1球后主胜 | 681 | 33.6% |
| `Both Teams To Score \| yes` | 双方都进球 | 1936 | 95.6% |
| `Multigoals \| 7+` | 总进球 ≥7 | 1817 | 89.7% |
| `Exact Goals \| 0` | 总进球 =0 | 1 | 0.05% |

### 互补性验证（关键）

**同一盘口的选项必须"不重叠、无遗漏"**：

```
1x2 三项：     并集 == 全集 ✓    交集 == 空 ✓
Total 2.5 大小：并集 == 全集 ✓    交集 == 空 ✓
```

如果并集不等于全集，说明有状态没人覆盖，会漏判。
如果交集不为空，说明有状态被重复覆盖，会重复计算成本。

**代码里的实现**：

```python
def build(pred):
    """给定一个判断函数，扫描全部 2025 个状态，生成 bitmask"""
    m = 0
    for i, (h1, a1, h2, a2) in enumerate(STATES):
        if pred(h1, a1, h2, a2):
            m |= 1 << i
    return m

# 例：主胜
covers_1 = build(lambda h1, a1, h2, a2: h2 > a2)

# 例：总进球 > 2.5
covers_over = build(lambda h1, a1, h2, a2: h2 + a2 > 2.5)
```

## 五、求解：整数规划

### 问题形式化

已知：
- 候选集 `C`，每个候选 `i` 有：
  - `mask[i]`：它覆盖的状态集合
  - `cost[i] = 1 / 赔率[i]`
- 全部状态 `S`（2025 个）

求：
- 一组候选 `X`，使得：
  1. **覆盖约束**：`∪ mask[i] = S`（所有状态都被覆盖）
  2. **成本最小**：`Σ cost[i]` 最小

### 数学表达

```
min  Σ (1/赔率ᵢ) × xᵢ           xᵢ ∈ {0, 1}

s.t. 对每个状态 s ∈ [0, 2025):
        Σ xᵢ ≥ 1                对所有覆盖 s 的 i
```

- `xᵢ = 1` 表示选中第 i 个选项
- 约束 2025 条，每个状态一条

### 实现

用 `scipy.optimize.milp`（底层是 HiGHS 求解器）：

```python
# 构造稀疏矩阵：行=状态，列=选项
# A[s][i] = 1 表示选项 i 覆盖状态 s
A = sp.csr_matrix((ones, (状态下标, 选项下标)), shape=(2025, n_options))

res = milp(
    c=cost,                                    # 目标：成本
    constraints=LinearConstraint(A, lb=1, ub=inf),   # Σ xᵢ ≥ 1
    integrality=np.ones(n),                    # xᵢ 是整数
    bounds=Bounds(0, 1),                       # xᵢ ∈ {0,1}
)
```

### 为什么必须精确求解，不能贪心

**贪心算法**：每次选"覆盖面最大 / 成本最低"的，直到全覆盖。

**问题**：贪心会先选大覆盖面，挤掉后面更优的小选项。

**实测**：

```
贪心结果：1.35
真实最优：1.02
误差：    +0.33（高估 32%）
```

具体例子：

| 候选 | 覆盖 | 成本 |
|---|---|---|
| A（覆盖全部） | 100% | 0.909 |
| B（覆盖 0,1） | 66% | 0.667 |
| C（覆盖 2） | 33% | 0.500 |

贪心：先选 A（单个最便宜）→ 0.909
最优：B + C → 0.667 + 0.500 = 1.167 ❌ 反例不成立

**换个更贴切的例子**：

| 候选 | 覆盖 | 成本 | 每格成本 |
|---|---|---|---|
| 大（覆盖 0,1） | 2 格 | 0.6 | 0.30 |
| 小（覆盖 2） | 1 格 | 0.5 | 0.50 |

贪心按"每格最便宜"选大（0.6），但状态 2 还没覆盖，得再选小（0.5）→ **总计 1.1**
而如果直接选"覆盖全部"的（0.909）→ **只要 0.909**

**贪心的选择依赖顺序，会走进死胡同。** 只有精确求解能保证全局最优。

## 六、完整流程

```
第 1 步：从数据库读该场全部选项
          ↓
          232 个选项（市场 + 归属 + 盘线 + 选项 + 赔率）
          ↓
第 2 步：过滤 + 转 bitmask
          ↓
          可建模 138 个 → [(mask, 赔率, 描述), ...]
          不可建模 94 个 → 丢弃（不影响判定）
          ↓
第 3 步：检查是否有状态无人覆盖
          ↓
          若有 → 返回 NO_COVER，该场跳过
          若无 → 继续
          ↓
第 4 步：整数规划求解
          ↓
          (成本, 选中的选项列表)
          ↓
第 5 步：覆盖验证（自检）
          ↓
          选中项的 mask 取并集，必须 == 全集
          ↓
第 6 步：判定
          ↓
          cost < 1.0  →  套利，写 kessbet_odds_hit
          cost >= 1.0 →  正常，记录成本
```

### 用真实数据走一遍

**比赛：Long An FC vs Thai Nguyen FC**

**第 2 步**：232 个选项 → 可建模 138 个

不可建模的 94 个：

|---|---|---|
| `Multiscores` | 11 | 比分组合，格式特殊 |
| `Or Both Teams To Score` | 4 | 复合盘口，语义未确认 |
| `Or Over 2.5` | 4 | 同上 |
| `To Score In Both Halves` | 4 | 未实现 |
| `1st Half - Double Chance` | 3 | 未实现 |
| … | | |

**第 3 步**：无覆盖缺口（状态 0~2024 都有候选覆盖）

**第 4 步**：ILP 求解，选中 3 个选项

| 选项 | 赔率 | 1/赔率 |
|---|---|---|
| `Exact Goals \| 0`（总进球恰为 0） | 9.80 | 0.102041 |
| `Multigoals \| 1-6`（总进球 1~6） | 1.06 | 0.943396 |
| `Multigoals \| 7+`（总进球 ≥7） | 35.00 | 0.028571 |
| **合计** | | **1.074008** |

**逻辑**：0 球 / 1~6 球 / 7+ 球，三种情况覆盖所有可能总进球。

**第 5 步**：覆盖 2025 / 2025 ✓

**第 6 步**：
```
成本 1.074008 > 1.0  →  无套利
投入 1.00 元，只能回收 0.9311 元，亏 0.0740 元
```

**对照纯 1x2 三项**：

```
1(5.20) + 2(1.56) + X(3.60) = 1.111111
```

**全盘最优 1.0740 < 纯 1x2 的 1.1111** —— 用 `Multigoals` 组合更省钱。

## 七、记录真实案例：1.0101 的异常定价

2026-10-28 扫描到最低成本 **1.0101**（CD Anaitasuna vs Alaves）：

```
1x2 | 1 (主胜)        = 50.00   →  1/50 = 0.020000
Double Chance | X2    = 1.01    →  1/1.01 = 0.990099
                                合计 = 1.010099
```

**为什么这组这么便宜？**

验算 `X2`（平或客胜）的合理赔率：

```
X2 应该 ≈ 1 / (1/15.00 + 1/1.04)
       = 1 / (0.0667 + 0.9615)
       = 1 / 1.0282
       = 0.9725
```

**理论赔率 0.9725 < 1**（不可能存在的赔率），平台却给了 1.01。

**这说明平台的 `X2` 定价有误**——它应该更接近 0.97，实际给了 1.01。

不过即使这样，成本 1.0101 仍然 > 1，不构成套利。

> **这类异常值得关注**：如果平台的 `X2` 继续调低（比如降到 0.99），
> 就会变成真实的套利机会。

## 八、已知的局限

### 1. 未建模的盘口不参与判定

现在有相当一部分盘口没有 `covers()` 实现：

| 盘口 | 状态 |
|---|---|
| `Halftime/Fulltime Correct Score` | ⚠️ 标签语义有歧义（`0:0 4+`） |
| `<队名> Or Any Clean Sheet` | ❌ 复合盘口（胜 **或** 零封） |
| `Draw Or Over/Under 2.5` | ❌ 未实现 |
| `Multiscores` | ❌ 格式特殊 |
| 角球 / 红黄牌 / 进球时间 | ❌ 不在比分空间内 |

**影响**：如果套利机会只存在于这些盘口的组合里，会漏掉。

**实测**：325 场扫描，全部能算出成本，说明主流盘口足够覆盖。

### 2. 状态空间有上界

```
半场 0..5，全场 0..9
```

超出这个范围的结果没建模。比如 10:0 的比分不在 2025 个状态里。

**影响**：理论上漏掉极端比分。但单队进球 ≥10 的概率极低（<0.01%）。

### 3. 比分盘的 `other` 是补集

`Correct Score` 有 `other` 选项，覆盖"所有未列出的比分"。

它的 mask 是 `全集 & ~已列比分`。

**如果某个比分超过 9:9，会落入 `other` 的范围——这是正确的**，因为 `other` 本来就代表"其他比分"。

### 4. 赔率会变

任何结论都是某一瞬间的快照。平台调价后结论可能变化。

## 九、判定标准

### 严格的数学定义

```python
if cost < 1.0:
    # 套利
```

**没有容差，没有四舍五入。**

`1.0000` 不算套利，`0.9999` 算。

### 为什么这么严格

因为**套利意味着"稳赚不赔"**。如果放宽到 `< 1.01`，那 1.005 的成本意味着：

```
投入 100.5 元，回收 100 元，亏 0.5 元
```

**这是亏钱，不是套利。**

### 现实中的分布

实测 195 + 325 场比赛：

| 统计 | 值 |
|---|---|
| 最低成本 | 1.0101 |
| 中位成本 | 1.0614 |
| 最高成本 | 1.1085 |
| **套利场次** | **0** |

**这符合理论预期**：最小覆盖成本 ≈ 平台的抽水水平。单家内部不可能出现套利。

def covers(market, side, line, label):

    elif base == 'Total' and line:

def solve(candidates, n_states):

## 附录：为什么不能只看 1x2

很多人会问：**直接看 1x2 三项的 `Σ(1/赔率)` 不就行了吗？**

不行，因为：

**1x2 是抽水最高的盘口之一。**

实测数据：

| 比赛 | 1x2 抽水 | 全盘最优 |
|---|---|---|
| Long An vs Thai Nguyen | 1.1111 | **1.0740** |
| 差异 | | **-0.037** |
