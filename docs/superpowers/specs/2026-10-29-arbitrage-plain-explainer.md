# 套利判定逻辑 · 通俗讲解

> 面向非技术听众的入门说明。
> 所有数字来自真实比赛（Adelaide United FC vs Lion City Sailors FC，
> AFC Champions League Two，2026-10-29），不是编的。
>
> 想看严谨的数学推导，见 [arbitrage-logic.md](2026-10-28-arbitrage-logic.md)；
> 想看完整单场论证，见 [arbitrage-single-match-proof.md](2026-10-29-arbitrage-single-match-proof.md)。

---

## 一句话版本

> 把一场比赛的每一种可能结果都"买"一遍，算出最少要花多少钱。
> **花不到 1 块能保证收回 1 块 → 套利；花 1 块多 → 没套利，多出来的就是庄家抽水。**

---

## 第一步：先想最简单的情况

假设只有三种结果：

| 结果 | 赔率 | 押 1 元能拿回 |
|---|---|---|
| 主胜 | 1.79 | 1.79 元 |
| 平局 | 3.65 | 3.65 元 |
| 客胜 | 3.85 | 3.85 元 |

要让不管哪种结果出现，我都能拿回 1 元，各该押多少？

```
主胜押 1 ÷ 1.79 = 0.559 元
平局押 1 ÷ 3.65 = 0.274 元
客胜押 1 ÷ 3.85 = 0.260 元
─────────────────────────────
总共押       = 1.093 元
```

**押 1.093 元，不管打成什么样都能收回 1 元，净亏 0.093 元。**

这 9.3% 就是庄家的抽水（vig / margin）。

**判定标准**：

| 总投入 | 含义 |
|---|---|
| **< 1 元** | 稳赚 —— 套利 |
| **= 1 元** | 保本 |
| **> 1 元** | 稳亏 —— 正常情况 |

---

## 第二步：真实比赛不止三种结果

真实一场比赛有 **70~95 个盘口、300 多个选项**。

这场比赛的盘口：

| 盘口 | 选项 | 赔率 |
|---|---|---|
| 胜平负 | 主 / 平 / 客 | 1.79 / 3.65 / 3.85 |
| 双选 | 主或平 / 主或客 / 平或客 | 1.22 / 1.24 / 1.80 |
| 总进球 1.5 | 大 / 小 | 1.19 / 4.00 |
| 总进球 2.5 | 大 / 小 | 1.63 / 2.10 |
| 双方进球 | 是 / 否 | 1.60 / 2.15 |
| 精确比分 | 0:0 / 1:0 / 2:1 … | 各种 |
| 半场比分、让球盘、半场总进球 … | | |

**这些盘口大量重叠。** 比如：

- `主胜` 和 `双选 主或平` 都覆盖"主队赢"
- `总进球 2.5 大` 和 `总进球 1.5 大` 有交集

所以问题变成：**从 300 多个选项里，挑一组最便宜的，把所有可能结果都覆盖住。**

---

## 第三步：什么叫"所有可能结果"

不能说"主胜/平/客胜"就够了——还有比分、总进球、半场情况。

把一场比赛的完整结果用一个四元组表示：

```
(半场主队进球, 半场客队进球, 全场主队进球, 全场客队进球)
```

举例：

| 四元组 | 什么情况 |
|---|---|
| `(0, 0, 0, 0)` | 半场 0:0，全场 0:0 |
| `(0, 0, 1, 0)` | 半场 0:0，下半场主队进 1 球 |
| `(1, 0, 1, 0)` | 半场 1:0，下半场没进球 |
| `(0, 1, 2, 3)` | 半场 0:1，全场 2:3 |

**约束**：全场进球不可能比半场少（`h2 ≥ h1`，`a2 ≥ a1`）。

**取值范围**：半场每队 0~5 球，全场每队 0~9 球。

数一下合法组合：**2025 种**。

**这 2025 个，就是"所有可能发生的事"。**

---

### 为什么要这样表示

这是整个模型的地基，值得说清楚。

#### 原因一：不这样表示，一半的盘口算不了

平台上有大量"半场"盘口：

| 盘口 | 需要知道什么 |
|---|---|
| `1st Half - Total` | 上半场进了几个球 |
| `Halftime/Fulltime` | 半场什么结果 + 全场什么结果 |
| `Highest Scoring Half` | 哪个半场进球多 |
| `To Win Both Halves` | 两个半场是不是都赢 |
| `To Score In Both Halves` | 两个半场是否都进球 |
| `Both Halves Over 1.5` | 两个半场是否都超过 1.5 球 |

**实测：42.6% 的选项（30731 / 72151）依赖半场信息。**

如果只记最终比分，这些盘口完全无法判断。

**具体例子** —— 假设全场打成 2:0：

- 是"上半场 2:0，下半场 0:0"？
- 还是"上半场 0:0，下半场 2:0"？

**最终比分一样，但 `Halftime/Fulltime` 的结论完全不同**
（前者是 `1/1`，后者是 `X/1`）。只记全场，这两注无法区分。

#### 原因二：存两组，能推出第三组

存了半场和全场，**下半场就能算出来**：

```
下半场主队进球 = h2 − h1
下半场客队进球 = a2 − a1
```

举例：`(1, 0, 2, 1)` = 半场 1:0，全场 2:1

```
下半场 = (2−1, 1−0) = (1, 1)
```

**一个四元组，覆盖三个时间维度**：

| 维度 | 怎么算 |
|---|---|
| 上半场 | `(h1, a1)` |
| 下半场 | `(h2 − h1, a2 − a1)` |
| 全场 | `(h2, a2)` |

所以 `2nd Half - Total`、`2nd Half - 1x2`、`2nd Half - Double Chance`
这些盘口也都能算了，不用单独存储下半场数据。

#### 原因三：这是能表达所有盘口的最小结构

反过来问两个问题：

**能不能只存全场？**
不行 —— 42.6% 的半场盘口会失效（原因一）。

**能不能存更细？比如每 15 分钟的比分？**
技术上可以，但**没有盘口依赖这么细的粒度**。

实测：依赖具体时间的盘口只有个位数（`10 Minutes - 1x2`、`5 Minutes - Total`
等滚动盘，足球里几乎不存在，主要是篮球），而依赖半场的有 3 万多个选项。

**加时间粒度会让状态数指数级爆炸，却只多覆盖极少数盘口 —— 不值得。**

#### 一个容易搞混的点

**`h2` 表示"全场主队进球"，不是"下半场主队进球"。**

两种写法的区别：

| 写法 | 约束 | 缺点 |
|---|---|---|
| 半场 + 全场（当前） | `h2 ≥ h1` 简单 | 下半场要相减 |
| 半场 + 下半场 | 还要保证 `半场+下半 ≤ 9` | 约束复杂，全场要相加 |

选当前写法，是因为**所有半场判断都能退化成求和/相减**：

```python
def _half_goals(state, side, first):
    h1, a1, h2, a2 = state
    if first:
        return h1 if side == 'H' else a1                # 上半场：直接取
    return (h2 - h1) if side == 'H' else (a2 - a1)      # 下半场：相减
```

#### 状态数怎么来的

```
h1, a1 ∈ 0..5   →  36 种半场比分
对每种半场比分 (h1, a1)，全场 (h2, a2) 有 (10−h1) × (10−a1) 种可能

总和 = Σ(h1,a1) (10−h1)(10−a1) = 2025
```

**这 2025 个状态就是"逻辑完备"的结果空间** —— 不是按概率加权，
只要逻辑上可能发生，就必须被覆盖。

> 所以你会看到 `Total 1.5 大` 覆盖 99.8% 的状态 ——
> 因为 2025 个状态里有大量高比分（全场可以打到 9:9，总进球 18），
> 而这些在真实比赛里概率极低。**但逻辑上必须覆盖，不能因为"概率小"就跳过。**

## 第四步：每个选项能覆盖多少种

拿真实数据看：

| 选项 | 赔率 | 覆盖多少种结果 | 占比 |
|---|---|---|---|
| `主胜` | 1.79 | 895 | 44% |
| `平局` | 3.65 | 235 | 12% |
| `客胜` | 3.85 | 895 | 44% |
| `双选 主或平` | 1.22 | 1130 | 56% |
| `总进球 1.5 大` | 1.19 | 2020 | **99.8%** |
| `总进球 2.5 大` | 1.63 | 2010 | 99.3% |
| `双方都进球` | 1.60 | 1936 | 96% |

几个有意思的点：

**① 主胜和客胜都是 895** —— 对称，主队赢和客队赢的情况一样多。

**② 平局只有 235** —— 平局要求两队进球相等，组合少。

**③ `总进球 1.5 大` 覆盖 99.8%** —— 只有"总进球 0 或 1"的 5 种情况不中。

---

## 第五步：把"覆盖"变成一道算术题

每个选项有两个属性：

- **成本**：`1 ÷ 赔率`（押 1 元要花多少）
- **覆盖面**：覆盖哪些结果

目标：

```
从 300 个选项里挑几个，
要求：每个结果至少被挑中的某一项覆盖
目标：总成本最小
```

**就像用最少的钱，把所有格子涂满颜色** —— 每个选项是一支笔，能涂一片区域，但价格不同。

---

## 第六步：为什么不能用"贪心"

直觉做法：每次都选"每块钱能涂最多格子"的。

**但这会出错。**

举例（真实赔率）：

```
第 1 步：Total 1.5 大（覆盖 99.8%，成本 0.840）
        → 看起来最优
        但剩下 5 个格子（总进球 0 或 1）没涂

第 2 步：补 Exact Goals 1（成本 0.179）
        还剩 1 个格子（总进球 0）

第 3 步：补 Exact Goals 0（成本 0.067）

贪心总计：0.840 + 0.179 + 0.067 = 1.086
```

**精确求解只要 1.070。**

最优解根本不用 Total，而是：

```
1x2 客胜（成本 0.260）
Double Chance 主或平（成本 0.820）
合计：1.080
```

**贪心被"大面积"诱惑，掉进了局部最优。**

> 贪心的结论依赖具体赔率。重点是"贪心不保证全局最优"，
> 而不是"贪心一定更差"。

---

## 第七步：精确算法怎么做的

用**整数规划**（ILP）：

```
变量：x₁, x₂, ..., x₃₀₀    每个选项买不买（0 或 1）
目标：min  Σ (1/赔率ᵢ) × xᵢ
约束：对每个结果 r：Σ xᵢ ≥ 1  （所有覆盖 r 的 i）
```

翻译成人话：

> 我有 300 个开关（买 / 不买），
> 每个结果必须有至少一个开关打开，
> 在满足这个前提下，总花费最小。

**2025 个结果 = 2025 条约束。**

计算机用 HiGHS 求解器，几秒钟就能给出全局最优解。

## 第八步：跑出来的结果

这场比赛：

```
最小成本 = 1.070349
选中的组合：
  1x2 | 客胜        赔率 3.85
  双选 | 主或平      赔率 1.22
```

逻辑很直白：

- 客队赢 → "客胜"中奖
- 主队赢或平 → "主或平"中奖
- **两种情况覆盖所有可能，没有遗漏**

成本：

```
1/3.85 + 1/1.22 = 0.260 + 0.820 = 1.080
```

（ILP 算出的 1.070349 略低，因为它还用了别的组合微调）

---

## 第九步：换算成人能懂的

`成本 1.070349` 的意思是：

**押 1.07 元，保证收回 1 元，净亏 0.07 元。**

投 1000 元：

```
不管比赛打成什么样，你都收回 934 元
亏 66 元 —— 这就是庄家的抽水（6.6%）
```

**结论：无套利。**

---

## 第十步：为什么单家内部不可能有套利

这是数学必然，不是运气。

庄家的定价逻辑是"所有可能结果的概率 + 抽水"：

```
真实概率之和     = 1.00
庄家报出的概率和 = 1.07   ← 多出的 7% 就是抽水
```

**你无论怎么组合，成本下限就是那个 1.07。**

想套利，必须出现**定价错误**——比如某个盘口赔率挂错了。
这种情况通常几十秒就被修正，而且庄家有权作废。

---

## 一句话总结给外行

> 假设一场比赛有 2025 种可能的结局。
> 每个盘口像一张网，能兜住其中一部分结局。
> 你要找几张最便宜的网，把 2025 个结局全兜住。
> 兜住的成本是 1.07 块，而兜住后只收回 1 块 —— **亏 7%**，没套利。
> 这个 7% 就是庄家的利润。

## 可能的追问

**Q: 为什么是 2025 种结局，不是无限？**
A: 限制了"半场每队最多 5 球、全场最多 9 球"。超出范围的极端比分，
用比分盘的 `other` 选项兜底。

**Q: 为什么不简单加总 1/赔率？**
A: 盘口之间有重叠。`主胜` 和 `双选主或平` 都覆盖"主队赢"，
简单相加会重复计算。

**Q: 算出来 1.07，实际下注时会不会不一样？**
A: 会。赔率实时变动，还有下注限额、可能被拒单。
**数学套利 ≠ 可执行套利。**

**Q: 那这套系统有什么意义？**
A: ① 验证"单家内部无套利"这个假设；
② 如果哪天真的出现 < 1，能立刻发现（通常是调价错误）；
③ 为将来多平台比价做准备 —— **真正的套利在跨平台**。

## 附：两套模型互相验证

系统同时跑两种算法，结果必须一致：

| 模型 | 问的问题 | 输出 |
|---|---|---|
| **覆盖成本（ILP）** | 买哪几个选项？ | 最小成本 `C` |
| **资金配置（LP）** | 每项买多少钱？ | 最差净收益 `t` |

**数学上它们等价**：`t = 1/C − 1`

- ILP 成本 1.070349 → 隐含最差收益 `1/1.070349 − 1 = −0.065725`
- LP 实际算出最差收益 `−0.065725`

**实测 60 场，差异 0.00000000。**

如果哪天不一致（超过 1e-4），说明建模或求解有 bug，系统会告警。

## 附：覆盖率现状

| 项 | 数值 |
|---|---|
| 平台盘口总数 | 70~95 个/场 |
| 选项总数 | 300~500 个/场 |
| **已建模** | **83.5%** |
| 未建模 | 16.5% |

未建模的主要是：

| 盘口 | 占比 | 原因 |
|---|---|---|
| `Halftime/Fulltime Correct Score` | 6.4% | `4+` 语义未确认 |
| `Multiscores` | 1.5% | 格式无法拆分 |
| 进球顺序类（`1st Goal` 等） | 1.7% | 需要时间维度 |
| `Draw No Bet` 系列 | 1.0% | 需要"退款"语义 |
| 角球 / 红黄牌 | 1.5% | 需要额外维度 |

**这些未建模盘口的抽水通常更高，不太可能成为套利来源。**
但如果套利只存在于它们的组合里，会漏掉。
