## 二、三处对原设计的修正

### 2.1 `is_complete()` 不能用标签集合判定

原设计（`2026-11-11-live-arbitrage-model.md` §4.2）：

> 如果 `Total From 76 To 80` 里混了 `line=0.5` 和 `line=1.5`，不能一起算。

**两个问题：**

① 窗口盘的 `line` 列**恒为空串**。实测 79 行窗口盘流水，`line` 全空，
阈值嵌在 `selection` 标签里（`'over 1.5'` 而不是 `'over'` + `line='1.5'`）。

② 按 `labels == {'over', 'under'}` 判定，会把**全部** Total 类判成残缺 ——
因为标签是 `'over 0.5'`。实测 161 种窗口盘里有 11 组因此「残缺」，全是误判。

**实际实现**（`analyze/live/window.py`）：按覆盖并集判定。

```python
def market_states(sels):
    """展开成状态空间 + 覆盖函数。"""
    if 任何标签以 over/under 开头:
        states = range(0, MAX_COUNT + 1)        # 事件计数
        cover  = lambda label, n: n > 阈值 或 n < 阈值
    else:
        states = ('1', 'X', '2')                # 窗口胜负
        cover  = lambda label, s: label == s
```

然后 `union(masks) == 全域` 才算完整。

### 2.2 跨盘线阶梯是合法组合，原设计漏了

`over 0.5` 覆盖 `n>=1`、`under 1.5` 覆盖 `n<=1`，并集就是全域。
原设计要求「同一盘线 over/under 配对」，会漏掉这类组合。

改成 ILP 后自动枚举到。实测里这种跨线组合确实出现过
（`over 0.5 + under 1.5`，Σ=1.1012，不构成套利但覆盖是满的）。

### 2.3 回测重建必须模拟「平台整组切盘线」

这是**最容易踩的坑**，我第一版就踩了。

直接按 `changed_time` 累加历史流水，会拼出幽灵套利：

```
第51分钟  over 1.5 @2.50  under 1.5 @1.37     盘线 1.5
第52分钟  over 0.5 @2.40  under 0.5 @1.40     整组切到 0.5
第53分钟  over 1.5 @2.80  under 1.5 @1.30     又切回 1.5
第58分钟  over 0.5 @5.00  under 0.5 @1.07     又切到 0.5
```

累加后状态里同时有「第58分钟的 over 0.5」和「第53分钟的 under 1.5」，
ILP 拼出 **Σ=0.9692** —— 但 under 1.5 早就撤了。第一版回测报了 14 个
这样的假命中，全是同一场比赛的同一份假数据。

**验证**：8094 个「同刻组」里，**0 例**跨盘线同时挂。平台从不这样做。

**正确重建**：每个盘口只维护当前盘线的腿；盘线变了整组替换；
同刻只有一条腿变时，另一条沿用该盘线上次的值（真实梯子）。

> 这和生产侧 `replace_live_odds` 的语义一致 —— 它拿 HTTP 全量接口的
> 当前状态覆盖，不在接口里的就删掉。

## 三、修掉的三个数据缺口

### 3.0 赛程接口不返回滚球比赛（最严重，已修）

**这是一个会让滚球采集永久漏场的结构性缺口。**

原来的采集路径：

```
赛前列表有它 → 存进 kessbet_match → 开赛后靠 kickoff_time 判断该采
```

前提是「开赛前至少被采到一次」。实测证明这个前提不成立：

```
ACTION=00252（赛程）timeslot='All'    123 场，ms 全部 = 0
              timeslot='Today'         32 场，ms 全部 = 0
              分页第二页                69 场，ms 全部 = 0
汇总 155 场                            开赛时间已过的：0 场
```

**赛程接口一场已开赛的都不返回。** 所以任何在赛前刷新间隙里上架、
或者因为分页/排序原因没被拉到的比赛，开赛后平台就再也不告诉你它存在。

实测缺口（2026-11-12 10:44）：

```
库内已知比赛 3,591 场
足球滚球       4 场，其中库里没有的 1 场  ← Club America vs Toluca
篮球滚球      11 场，其中库里没有的 7 场
```

**解法：用网页 Live 页的接口 `ACTION=00232`。**

从浏览器抓包 + 解密请求体得到的参数：

```json
header: {"action": "00232", ...}
body:   {"tabId": "1", "playType": "1", "sortBy": 6, "specifiers": ""}
```

实测行为：

| 参数 | 观测 |
|---|---|
| `tabId` | 按运动区分，和赛前的 `SPORTS` 映射一致（1=足球、8=篮球） |
| `playType` | 0~4 和空串结果完全相同，**无实际作用** |
| `sortBy` | **0 会漏**（2 场而不是 3 场），1~7 都全；3 返回另一种结构 |
| 分页 | 一次返回全部，不需要游标 |

返回的 `matchList` 里每场都带 `ms`（6/7/31）、`mt`、`hmp`/`amp`、
角球，外加一份 `mari`（当前主盘口）—— 正是滚球采集需要的。

**接入方式**：`Collector.refresh_live_schedule()` 每 `LIVE_SCHEDULE_SEC`
（默认 60 秒）拉一次，只把库里还没有的比赛 `upsert` 进去。
实测补采 8 场后缺口归零。

为什么只插不存在的：每 60 秒拉一次，把 4000 场全 upsert 一遍是
无谓的写入。`known_match_ids()` 一次查一列（约 100KB），够快。

### 3.1 `kessbet_odds_live` 没有删除逻辑（已修）

赛前那边 `collect/writer.py` 做了 `stale = db_keys - fresh_keys` →
`log_removed` → `delete_keys`。滚球这边**漏了**，只 INSERT + UPSERT。

实测后果（比赛 890254，篮球进行中）：

```
平台实时返回   170 个选项
表内           353 个选项
滞留（已撤）   241 个选项 / 43 种盘口
```

足球场次更严重：第 85 分钟时表里还留着 `From 61 To 75` 的窗口盘。
重建快照统计，2236 个「快照 × 窗口盘」里 **1244 个（56%）窗口已过期**。

虽然这次实测没造出 `Σ<1` 的假信号（运气，不是设计保证），但这是
数据正确性的硬缺口。已在 `db/dao.py:replace_live_odds` 补上。

### 3.2 「35% 残缺率」是假数字（已撤）

`2026-11-09-live-arbitrage-design.md` §3.2 和复核文档 §5.2 都引用了
「31 组里 11 组残缺（35%）」，还拿它论证 `is_complete()` 不能省。

按 `(match, market, side)` 正确分组重算：

| 数据源 | 组数 | 残缺 |
|---|---|---|
| `kessbet_odds_prematch` | 34 | **0** |
| `kessbet_odds_history` | 30 | **0** |

那 11 组恰好全是 Total 类 —— 被「标签带阈值」这一个格式差异误杀。

**结论不变**（`is_complete()` 仍然必须做，这是防线），
但对数据质量的判断改了：滚球窗口盘本身很完整，
131 个重建快照里只有 3 例真残缺，且都在盘口刚上下架的 1~2 秒内。

## 四、代码结构

```
analyze/live/
├── __init__.py
├── window.py     模型 A 核心：解析盘口名、状态空间、完整性、判定
└── run.py        主循环：读库 → 判定 → 写快照 + 成本表

db/dao.py
├── live_analyze_targets()      找出要判定的比赛（窗口内 + 有赔率）
├── get_live_selections()       读一场的滚球选项
├── replace_live_window_costs() 写窗口成本（整场替换）
├── list_live_window_costs()    读成本（按成本升序）
└── replace_live_odds()         已补删除逻辑

db/schema.sql
└── ⑫ kessbet_live_window_cost  新表：一场多行，记录每个窗口盘的成本

web/live.html         列表页（点行进详情）
web/live_detail.html  详情页（计分板 + 窗口成本 + 走势 + 全部盘口）

web/api.py
├── GET /api/live/window-costs         全局窗口成本（列表页用）
├── GET /api/live/{match_id}           详情（盘口 + 窗口成本）
└── GET /api/live/{match_id}/history   单选项赔率走势
```

**判定速度**：59475 组求解用 8 秒。快的原因是在 `window._solve_masks()`
里加了快速路径 —— 1x2 三选、over/under 配对这类「互斥且满覆盖」的盘口，
唯一可行解就是全选，成本必然是 Σ(1/赔率)，不需要 ILP。
实测绝大多数窗口盘走这条路径，只有跨线阶梯才真跑 solver。

### 4.1 详情页

滚球列表点任意一行 → `/live/<match_id>`，页面包含四块：

| 区块 | 内容 |
|---|---|
| 计分板 | 比分、状态+分钟、角球、黄牌、盘口/选项数 |
| 窗口盘成本 | 每个窗口盘一行，按成本升序。这是模型 A 的判定依据 |
| 赔率走势 | 点任意选项看它的变动序列，每点带当时的分钟和比分 |
| 全部盘口 | 按 (market, side) 分组，窗口盘标注「剩余时间」 |

URL 支持两种形态：`/live/<id>`（列表点进来）和 `/live/detail?id=<id>`（分享用）。

## 五、怎么跑

```bash
# 单轮（调试）
py -m analyze.live.run --once -v

# 常驻（独立进程）
py -m analyze.live.run --interval 10

# 或者跟赛前分析一起跑（推荐，共用连接和调度）
py -m analyze.run        # LIVE_ENABLED=True 时会自动带上滚球判定
```

**已接入 `analyze/run.py` 的主循环**，不需要单独起进程。
滚球判定每 `LIVE_ANALYZE_SEC`（默认 10 秒）跑一次，和赛前的 2 秒
节拍独立。间隔比赛前宽是有意的：窗口盘的机会来自平台定价失误，
不是毫秒级抢跑。

## 六、实测数据一览

### 6.1 窗口盘类型分布（161 种）

| 后缀 | 种类数 | 跨度 | 标签 |
|---|---|---|---|
| `1x2` | 28 | 5/10/15 | `1` `X` `2` |
| `Corner 1x2` | 27 | 5/10/15 | `1` `X` `2` |
| `Booking 1x2` | 24 | 5/10/15 | `1` `X` `2` |
| `Total` | 29 | 5/10/15 | `over/under 0.5/1.5/2.5` |
| `Total Corners` | 30 | 5/10/15 | `over/under 0.5/1.5/2.5` |
| `Total Bookings` | 23 | 5/10/15 | `over/under 0.5/1.5` |

**窗口出现时机**：平台从第 46 分钟才开始挂（`From 46 To 50` 是最早的）。
比赛前半段窗口盘数是 0 —— 这是平台行为，不是采集故障。

### 6.3 `ms=31` 是中场休息（2026-11-12 补充）

原来只映射了 `0/6/7/100/120`，实测发现足球中场时状态码是 **31**：

```
2026-11-12 10:01 同时 3 场停在这个状态
  Deportes Quindio   minute=50  0:0
  CD FAS Santa Ana   minute=48  2:1
```

有比分、有分钟、有角球，只是停在 45~50 不动 —— 典型的中场。
之前页面显示成「未知(31)」。

**`LIVE_STATUS` 不参与任何判断**（只有 `FINISHED_STATUS` 生效），
所以漏了这个码不会导致误判，只是显示难看。但这也说明：
**「该不该采」要用黑名单（终态）而不是白名单（进行中）** ——
白名单会让没见过的状态码被静默跳过。

### 6.4 `status` 列溢出 —— 状态码不要假设范围（2026-11-12 补充）

`kessbet_match_live.status` 原本是 `TINYINT`（上限 127）。实测美式足球
返回 **`ms=303`**，写入直接失败：

```
(1264, "Out of range value for column 'status' at row 1")
```

已改成 `SMALLINT`。教训和 6.3 是同一个：**状态码是平台私有编号，
不要假设它的取值范围**。同理，页面上的状态标签也改成
「未知码不吓人」的写法（`进行中 · 码 303`），而不是 `未知(303)`。



### 6.2 成本分布（回灌的历史，1067 行）

```
最低  1.1023
平均  1.1360
最高  1.1598
```

最低的 1.1023 是 `15 Minutes - Total Bookings From 61 To 75`，
和 11-09 那次赛前采样（1.095~1.153）同一量级。两批独立数据吻合。

## 七、模型 B 的前置条件确认

`2026-11-11-live-arbitrage-model.md` §4.2 说 B2 路径「状态数虽然比 B1 多，
但仍是 2025 的子集，求解可接受」。**实测这个说法不成立：**

| 当前比分 | 只锁终局 `h2>=H,a2>=A` | 再锁半场 `h1,a1` | 倍数 |
|---|---|---|---|
| 0:0 | 2025（100%） | 100 | 20x |
| 1:0 | 1980（98%） | 90 | 22x |
| 1:1 | 1936（96%） | 81 | 24x |
| 2:1 | 1848（91%） | 72 | 26x |

**只锁终局在 1:0 时还剩下 98%**，ILP 单场 1.2 秒的开销一分没省。
必须等中场休息后**连 `h1/a1` 一起锁**，才能降到 4%~5%。

这一步是安全的：`covers()` 的全场分支只依赖 `h2/a2`，锁半场不改变
mask 语义（验证过 `Total over 2.5` 在 `h1=1,a1=0` 切片内覆盖率仍正确）。

### 一个实操坑：状态空间上界

`STATES` 里全场进球上限是 9（`G=10`）。滚球到 5:4 时，
「6:4 … 9:9」这些终局在抽象空间里可达，但平台根本不挂对应的
Correct Score 盘线 → 必然 `NO_COVER`。

正确做法是把子集上界收紧到「平台当前给出的最高 Total 盘线」：

```python
max_line = max(float(s.line) for s in total_sels)   # 例如 5.5
S = [s for s in S if s[2] + s[3] <= ceil(max_line)]
```

否则 `NO_COVER` 会混着「我们的状态空间想太多了」和「真的没盘口」。

### 半场比分从哪来

`fetch_state` 的 `msScoreList` **不能直接用** —— 实测当前比分 0:1 时
它返回两个 0:0 的阶段快照。可行来源有两个：

1. 平台若在半场后更新 `msScoreList` 里的半场阶段 —— **待验证**
2. 从自己的流水表反推：取 `minute <= 45` 的最后一条 `home_score/away_score`

方案 2 的数据已经在采，作为兜底可靠。
